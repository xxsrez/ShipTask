# Режимы исполнения Issue Grinder

Статус: реализованная схема, 2026-09-04. Этот документ объясняет текущее
решение, но не является самостоятельным источником policy. Действующую норму
задают [Overview](../skills/issue-grinder/overview.md),
[Requirements](../skills/issue-grinder/requirements.md),
[Architecture](../skills/issue-grinder/architecture.md) и скомпилированный из
них runtime skill.

Пользовательские режимы: `Соло`, `Классический`, `Баланс`, `Менеджер` и
`Экономичный`. Если пользователь не назвал режим явно, всегда выбирается
`Соло`. Модель, размер scope, остаток квоты и доступность Luna не меняют этот
выбор автоматически.

Для выбора режима без инженерных деталей используйте
[пользовательский мануал](../guides/issue-grinder-modes.md).

## 1. Цели

1. `Соло` медленно и экономно доводит сложный scope одним основным агентом.
2. `Классический` сохраняет максимальную уверенность на сложной работе и
   отдаёт Luna только строго простые пакеты.
3. `Баланс` ускоряет тяжёлую работу относительно последовательного `Соло`:
   основной агент сохраняет архитектуру, интеграцию и финальное решение, а
   Luna параллельно реализуют несколько безопасных независимых частей.
4. `Менеджер` заменяет значительную часть дорогой работы устойчивой Luna Loop:
   постоянный manager ведёт постоянного implementer-а по крупным фазам, затем
   один reviewer проверяет целый кандидат.
5. `Экономичный` выжимает максимум безопасного результата из Luna и допускает
   честную возобновляемую контрольную точку вместо ложного terminal результата.
6. Все режимы сохраняют одинаковые authority, scope, evidence и safety
   boundaries.

## 2. Не цели

Режимы не:

- выбираются автоматически по модели, квоте, размеру задачи или числу issue;
- обещают выигрыш времени на scope без независимых частей и долгих проверок;
- разрешают параллельные изменения одного writable surface;
- размножают production, shared-state, платные или необратимые эффекты;
- принимают отчёт subagent-а вместо проверки exact integrated candidate;
- считают число агентов, токенов или строк кода доказательством качества.

## 3. Общие инварианты

- До записи разрешаются точный scope, authority, repository и integration
  target.
- Один writable surface имеет одного owner-а. Параллельные writers работают в
  отдельных worktree либо shadow tree.
- Integration owner механически объединяет точные handoff-ы и проверяет уже
  объединённый результат.
- Спекулятивно параллелятся только локальная работа и обратимые проверки.
  Внешний или необратимый эффект исполняется один раз после обычного gate.
- Нормальный subagent path содержит один guard, один dispatch и событийное
  ожидание до deadline всей стадии. Частый polling не является управлением.
- Режим не меняется сам. Смена действует только после явной просьбы
  пользователя и сохраняет полезный checkpoint.
- В проектируемом окружении Luna считается доступной. Runtime не содержит
  отдельной политики подмены недоступной Luna основным профилем.

## 4. Сводная схема

| Режим | Кто владеет задачей | Luna | Приёмка | Допустимый итог |
|---|---|---|---|---|
| `Соло` | Текущий основной агент | Нет | Self-review основного агента по объективному evidence | Terminal |
| `Классический` | Основной controller | Только strict-simple пакеты, Luna Max | Независимый review exact candidate и финальное решение controller-а | Terminal |
| `Баланс` | Основной агент | Одна волна из 2–3 Luna High writers | Один exact-diff pass основного агента; отдельного reviewer-а по умолчанию нет | Terminal |
| `Менеджер` | Основной coordinator и постоянный Luna manager | Manager, implementer и reviewer на Luna Max | Reviewer после manager `complete`, затем финальный gate coordinator-а | Terminal |
| `Экономичный` | Luna coordinator | Почти вся работа и review на Luna Max | Economical review либо явно deferred gate | Terminal или resumable checkpoint |

Внутреннее значение `swarm` остаётся совместимым wire identifier режима
`Менеджер`; прежнее пользовательское имя больше не используется.

## 5. `Соло`

`Соло` — безусловный режим по умолчанию и ориентир для тяжёлой задачи.
Текущая top-level model с текущим effort одна читает scope, принимает решения,
изменяет код, запускает проверки и делает self-review. Worker, manager, critic,
reviewer и competing candidate не создаются. Рабочие пакеты выполняются
последовательно, но независимые tool-bound проверки может запускать параллельно
сам основной агент.

## 6. `Классический`

Основной controller читает весь scope, строит dependency graph, владеет
архитектурой и material judgment. Luna Max получает только bounded,
self-contained, low-risk пакет с отдельной поверхностью записи и локальным
oracle. Controller подхватывает всё, что перестало быть простым, объединяет
кандидат и принимает его после независимой проверки. Режим продолжает работу до
terminal результата либо доказанного terminal blocker-а.

## 7. `Баланс`

### 7.1 Назначение

`Баланс` — ускоренный вариант уверенного main-owned исполнения. Он должен
сохранять качество сложного `Соло`, добавляя небольшой расход основного
профиля, и выигрывать календарное время за счёт перекрытия независимой
разработки и реальных tool-bound проверок.

### 7.2 Допуск параллельной волны

Основной агент один раз читает весь scope, фиксирует архитектуру, acceptance,
dependency graph и surfaces. Волна создаётся только когда найдены как минимум
два, но не больше трёх пакетов, каждый из которых одновременно:

- dependency-ready и имеет ясный independently verifiable outcome;
- self-contained и не требует самостоятельного архитектурного решения;
- владеет непересекающейся поверхностью записи;
- изолирован от shared mutable state и внешних эффектов;
- имеет стабильный интерфейс и локальный oracle;
- достаточно содержателен, чтобы dispatch и fan-in окупались.

Если двух таких пакетов нет, основной агент продолжает последовательно без
искусственного распараллеливания.

### 7.3 Исполнение

- Создаётся одна активная волна из 2–3 Luna High writers.
- Каждый writer получает компактный frozen packet: outcome, owned files,
  запреты, локальный oracle и формат handoff. Он не перечитывает весь проект, не
  строит свою архитектуру, не запускает descendants или long-running gates.
- Основной агент не ждёт без дела: одновременно выполняет отдельную
  интеграционную, CLI или другую main-owned часть критического пути.
- После dispatch используется одно коллективное event-driven ожидание. Нет
  периодических list/status/nudge и промежуточных пересказов.
- Handoff содержит candidate identity, owned bytes, выполненные быстрые
  проверки, открытые риски и сведения о базе. Полный patch не переносится в
  разговор, если его можно прочитать механически.
- Неудачный или неполный handoff не порождает manager, reviewer либо цепочку
  повторных агентов: основной агент принимает владение и исправляет остаток.

### 7.4 Fan-in и проверки

Основной агент проверяет identity и ownership, механически объединяет handoff-ы
и смотрит exact integrated diff. Независимые длительные tool-bound gates
запускаются одним параллельным batch, затем выполняется общий integration gate.
Основной агент устраняет findings и сам принимает итог. Отдельный independent
reviewer не является штатной ролью `Баланса` и появляется только по явному
требованию пользователя или проекта.

Наблюдаемое нарушение режима: serial dispatch независимых writers, несколько
active waves, Luna manager/reviewer, nested delegation, polling, дублирование
main и worker работы, fan-in по пересказу либо terminal claim без проверки exact
candidate.

## 8. `Менеджер`

Основной coordinator передаёт одному постоянному Luna Max manager-у control
brief и точный task-owned candidate. Manager сам не пишет product source и по
одной крупной фазе направляет одного постоянного Luna Max implementer-а.
Каждая фаза имеет bounded outcome и oracle; следующая начинается после принятия
предыдущей manager-ом.

После завершения всех фаз один постоянный Luna Max reviewer без descendants
проверяет exact candidate по крупным risk sections. Material rework возвращается
тому же implementer-у, а изменённый кандидат — тому же reviewer-у. Coordinator
сохраняет Goal, Task Manager, authority, внешние эффекты, интеграцию и финальное
решение. Несколько менеджеров, одновременные фазы и competing implementations
не являются штатным путём.

## 9. `Экономичный`

Luna Max coordinator распределяет bounded работу Luna workers, объединяет один
кандидат и организует независимую economical проверку. Основной профиль почти
не используется. При исчерпании разрешённого бюджета или невозможности честно
закрыть дорогой gate режим сохраняет точный candidate, evidence, unresolved
risks и следующий шаг как resumable checkpoint; незавершённость не маскируется
terminal статусом.

## 10. Resolver и переключение

Resolver выполняется один раз в начале run:

1. Нормализует явное имя или однозначный пользовательский синоним.
2. Если выбора нет, фиксирует `Соло`.
3. Сохраняет canonical mode в run-state и использует его до явной смены.

При смене режима сохраняются candidate identity, owners, commits, worktrees,
checks и unresolved risks. Уже выполненная работа не повторяется только ради
новой topology. Внешние эффекты не переигрываются.

## 11. Наблюдаемая оценка

Для каждого прогона отдельно фиксируются:

- terminal outcome и качество public/hidden oracle;
- wall-clock time;
- Sol, Luna и иные модели отдельными строками telemetry;
- cached input, uncached input и output по фактическому
  `last_token_usage` каждой сессии;
- число writers, волн, ожиданий, fan-in и review stages;
- выполненный объём работы и существенные отклонения от mode contract.

Небольшой дефект измерителя не останавливает серию: он отмечается рядом с
затронутой метрикой. Дефект, меняющий сопоставимость всей серии, указывается
отдельно рядом с итоговой таблицей. Для `Баланса` дополнительно проверяются
одна волна, 2–3 Luna High writers, полезная параллельная main-работа, одно
коллективное ожидание, параллельные tool gates, отсутствие штатного reviewer-а
и финальная приёмка exact candidate основным агентом.

## 12. Трассировка

Нормативная трасса текущего решения:

`Overview | Requirements | Architecture → issue-grinder/SKILL.md + references
+ routing guard + mode harness → contract tests + synthetic evaluation`.

Requirements определяют ожидаемое поведение, Architecture — способ его
достижения, runtime — исполняемую инструкцию, а evaluation — наблюдаемое
доказательство. Исторический benchmark или отчёт не становится скрытой policy.
