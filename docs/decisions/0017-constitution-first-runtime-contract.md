# 0017. Constitution-first runtime contract

Статус: partially superseded, 2026-08-21. Outcome-level требования сохраняются,
а обязательная последовательность восстановления инструментов заменена
[ADR-0018](0018-outcomes-not-tool-choreography.md), selector-based Goal policy —
[ADR-0019](0019-goal-only-for-multi-task-implementation.md).
Это решение ввело ShipTask lifecycle, обязательные комментарии и свободу исполнения.
Оно частично заменяет ADR-0009, ADR-0010, ADR-0013, ADR-0015 и ADR-0016 там,
где те задавали иной порядок status/comment effects, разрешали менять status с
отложенным comment, фиксировали число проходов либо превращали
внутреннюю процедуру в пользовательское требование.

## Контекст

Предыдущий контракт подробно предписывал порядок классификаций, Goal turns,
report states, повторов и внутренних handoff. Он должен был обеспечить
правильный результат, но стал самостоятельной бюрократической системой. Агент
проверял соблюдение внутренних шагов и терял реальные требования пользователя.

Практический сбой показал это особенно ясно: Task была возвращена из review без
объясняющего комментария, недоступный обязательный инструмент не стал главной
проблемой run, а ответ в сессии подменил durable handoff в Task. Формально
правдивый status не компенсирует отсутствие требуемого объяснения.

## Решение

### Конституция вместо сценария по шагам

Runtime задаёт небольшой набор обязательных результатов и границ. Агент свободен
выбирать инструменты, порядок работы, реализацию, диагностику и достаточные
проверки. Подробные examples и eval cases проверяют contract, но не становятся
универсальным алгоритмом.

### Комментарий — часть существенного перехода

Любой существенный status transition состоит из трёх наблюдаемых effects:

1. понятный native Task comment;
2. read-back этого comment;
3. status write и Task read-back.

Порядок именно такой. Исключение — обычный старт `To Do → In Progress`.
Material blocker тоже документируется comment, даже без status change. Codex
answer, Goal, plan, reason code, `description` или другой field comment не
заменяют.

Если comment channel не работает и не восстановлен, существенный transition не
выполняется. Старое правило, при котором status менялся с отложенным comment,
исключается из current contract.

### Сломанный необходимый инструмент — сначала предмет работы

Агент обязан установить причину отказа и попытаться безопасно восстановить
основной способ до обхода. После material repair повторяется исходная операция.
Альтернатива допустима только при равной доказательной силе; ослаблять acceptance
ради завершения нельзя.

Нет business-счётчика попыток. Повтор оправдан новым состоянием или исправлением.
Stop оправдан только когда продолжение требует новой authority, внешнего state
change или небезопасного действия. Тогда причина, impact и условие
возобновления объясняются прямо.

### Приёмка различает четыре фактических исхода

- противоречие current Task contract;
- доказанный product defect;
- невозможность доказать success или failure;
- доказанный success.

При доказанном defect сначала публикуется причина возврата, затем Task переходит
в `In Progress`, а исправление продолжается в том же run. При невозможности
приёмки сначала восстанавливаются нужные инструменты; если это невозможно,
Task остаётся `In Review`, а comment даёт краткие варианты проведения приёмки.
При success completion comment предшествует `Done`.

### Strategic Explainer — помощник по смыслу, не управляющий слой

Он помогает сформулировать каждый обязательный lifecycle/blocker comment на
уровне проблемы, влияния, ограничения и следующего шага. ShipTask сохраняет
ответственность за facts, status, authority, action и final wording. Bounded
read-only discovery применяется по необходимости, а не ради полноты ритуала.

### Goal — только учёт batch progress

Goal не определяет Task outcome, количество повторов или остановку. Task-local
blocker оставляет его активным. Complete допустим только после fresh inventory
без незавершённой in-scope работы.

## Последствия

- Runtime становится короче и оставляет агенту пространство для инженерного
  решения.
- Пользовательские требования проверяются напрямую по Task state, comments,
  evidence и result, а не по внутренним названиям шагов.
- Отсутствующий обязательный comment больше нельзя представить завершённой
  коммуникацией.
- Поломка необходимого инструмента становится явной причиной работы или
  остановки, а не скрытым поводом ослабить проверку.
- Исторические ADR и reports сохраняются как история, но не являются fallback
  policy для current runtime.
