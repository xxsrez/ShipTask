# Scope Reviewer: требования пользователя

Статус: current Level 1, 2026-09-02.

Этот документ — полный пользовательский исходный код только для Scope Reviewer.
Он не определяет требования Task Composer, Issue Grinder, Strategic Explainer
или Task Manager; их использование ниже является локальной dependency Scope
Reviewer.

Требования задают обязательный outcome, rationale, observable evidence и
scope/truth/safety/authority boundaries. Architecture и будущий runtime могут
переформулировать и конкретизировать их, но не могут ослабить, заменить или
молча удалить. Изменение смысла Level 1 требует явного решения пользователя.
Число оптик, форма внутренних пакетов, порядок чтения и записи, структура
отчёта и другие вопросы реализации остаются свободными, если точный механизм не
назван здесь отдельным инвариантом.

`architecture.md` хранит agent-owned current способ достижения этих требований.
Будущий runtime package должен быть компактной смысловой компиляцией локальных
Overview, Requirements и Architecture. Если runtime удалить и пересобрать из
этих трёх документов, новый skill должен быть примерно эквивалентен по всем
требованиям `SR-*` и выбранной архитектуре.

## Требования

### `SR-01` — Один понятный обзор выбранного scope

Scope Reviewer принимает однозначно выбранный Task Manager Project, Release,
Epic, Task или связный набор Tasks и возвращает один целостный отчёт о нём.
Отчёт не заставляет человека читать все карточки или внутренние технические
материалы, чтобы понять общую картину.

Если scope нельзя определить однозначно, skill не угадывает его по последнему,
самому новому или похожему объекту и не смешивает несколько возможных scope в
один результат.

### `SR-02` — Актуальная и правдивая картина

Анализ опирается на current состояние всего выбранного scope, включая
Strategic Outcome, Human Requirements, Agent Plan, hierarchy, relations,
statuses и доступное evidence. Эти три смысловые роли не смешиваются: общий
ориентир объясняет направление, Requirements задают защищённые обязательства
человека, а Plan описывает изменяемый способ их выполнения. Факт, план,
предположение, риск, неизвестное и ещё не проверенный результат остаются
различимыми. Изменившийся во время анализа scope не представляется как единый
согласованный snapshot.

Task Manager state доказывает только собственную projection. Код, интеграция,
тестирование, выпуск и другие внешние результаты считаются достигнутыми только
при наличии соответствующего evidence.

### `SR-03` — Независимый анализ через уместные оптики Luna Max

Основной агент самостоятельно определяет набор materially useful оптик для
конкретного scope. Каждая выбранная оптика получает отдельного независимого
`gpt-5.6-luna` subagent с `reasoning_effort="max"`, который глубоко анализирует
scope именно с этой точки зрения и ясно формулирует значимые выводы.

Число оптик не фиксировано и не увеличивается ради формальной полноты. Оптика,
не способная изменить понимание плана или состояния, решение, исправление,
риск, действие либо уверенность, не должна создавать шум в итоговом отчёте.

### `SR-04` — Защищённые Requirements человека

Human Requirements являются отдельным согласуемым источником и не изменяются
Scope Reviewer. Skill вправе обнаружить в них противоречие, пробел, неясность,
непроверяемое ожидание или material выбор, но возвращает человеку вопрос,
объяснение влияния и при необходимости варианты решения вместо автоматической
правки.

Ни уверенность агента, ни согласие нескольких оптик, ни удобство реализации не
разрешают переписать, ослабить, расширить, удалить или молча переосмыслить
Requirements. После явно согласованного человеком изменения Requirements план
обновляется относительно нового источника и проходит повторное ревью.

### `SR-05` — Автоматическое улучшение agent-owned плана

По явному intent улучшить или подготовить план Scope Reviewer самостоятельно
исправляет обнаруженные проблемы во всей доступной ему agent-owned planning
model, не требуя от человека утверждать каждую техническую правку. Исправления
могут затрагивать детализацию Tasks, decomposition, acceptance, expected
evidence, dependencies, hierarchy, relations и другие изменяемые части плана,
если они сохраняют Requirements, exact scope и authority boundaries.

Scope Reviewer может уточнить формулировку Strategic Outcome и перестроить Agent
Plan, чтобы работа лучше служила общей цели, если при этом не меняется
пользовательский смысл. Material изменение самой проблемы, желаемого результата
или Human Requirements остаётся решением человека.

Простой запрос показать, объяснить, проверить или дать status report остаётся
read-only и сам по себе не разрешает planning mutations. Частичный или
неподтверждённый repair не называется успешно обновлённым планом.

### `SR-06` — Requirements review как отдельная обязательная оптика

При ревью плана одна из оптик проверяет человеческие Requirements на внутренние
противоречия, неоднозначность, пропуски, скрытые решения и невозможность
объективно понять достижение результата. Эта оптика не подменяет человека и не
выбирает продуктовый смысл, но делает material проблему достаточно понятной для
обсуждения и решения.

Та же оптика проверяет происхождение обязательств: предположение агента,
необязательный hardening, удобная техническая практика или широкая формулировка
Strategic Outcome не должны быть выданы за Human Requirement, обязательную
проверку либо blocker.

### `SR-07` — Повторяемый цикл до готовности плана

После автоматических исправлений Scope Reviewer перечитывает актуальный план и
повторяет применимые проверки. Если остаётся вопрос к Requirements, skill
отделяет его от автоматически исправимых проблем и возвращает человеку. После
согласования Requirements и обновления плана review запускается заново.

План признаётся готовым к передаче в исполнение только когда Tasks совместно
покрывают согласованные Requirements, существенные planning-проблемы устранены,
dependencies и acceptance согласованы, а нерешённые вопросы и необходимое
участие человека названы честно. Scope Reviewer не запускает исполнение только
из-за достижения этой готовности.

Стратегическая связность используется для улучшения решений и выявления
пробелов, но не требует доказать исчерпывающее достижение широкого Strategic
Outcome как отдельное условие readiness поверх согласованных Human Requirements
и формального Task scope.

### `SR-08` — Осмысленная композиция вместо свалки отчётов

Основной агент собирает результаты оптик, удаляет несущественные и повторяющиеся
наблюдения, объединяет совместимые выводы и сохраняет material disagreement.
Итоговый отчёт является новой целостной композицией, а не последовательной
вставкой всех ответов subagents, техническим журналом или пересказом списка
Tasks.

### `SR-09` — Человекочитаемый и лёгкий итоговый отчёт

Отчёт написан естественным языком, быстро передаёт главную причинную картину и
остаётся понятным без погружения в технические детали конкретной реализации.
Он сохраняет необходимую точность, ограничения и неопределённость, но не
перекладывает на читателя расшифровку внутреннего жаргона, статусов агентов,
идентификаторов и служебного процесса.

При активной модели Astra (`gpt-6-astra`) Scope Reviewer формулирует такой
отчёт самостоятельно и не вызывает Strategic Explainer; native report проходит
тот же factual и reverse-coverage контроль.

Глубина анализа не превращается в объём публикации. Материал, который ничего не
меняет для понимания, решения, риска, действия или уверенности человека, в
итоговый текст не попадает.

### `SR-10` — Полная visibility для планирования

Отчёт о плане позволяет человеку понять:

- какую проблему решает scope и какой будущий результат ожидается;
- чем Strategic Outcome, Human Requirements и Agent Plan отличаются в этом
  scope;
- где система или продукт находится сейчас и что должно измениться;
- как Tasks совместно дают этот результат без пересказа каждой карточки;
- какие проблемы исправлены автоматически;
- какие риски, blockers, зависимости и неизвестные остаются;
- где потребуется review или помощь человека, почему и в какой момент;
- где участие человека не требуется;
- готов ли план к исполнению и на каком основании.

Эти смысловые вопросы не являются обязательным шаблоном или набором заголовков:
структура и длина следуют конкретному scope.

### `SR-11` — Такой же обзор текущего Release

Во время исполнения Scope Reviewer по тем же принципам возвращает понятный
read-only отчёт о current Release или другом выбранном delivery scope. Человек
видит фактически достигнутый результат, текущее состояние относительно общей
цели, оставшуюся существенную работу, критический путь, риски, blockers,
следующее ожидаемое состояние и необходимость своего участия.

Отчёт отдельно показывает формальную полноту Task scope и степень достижения
более широкого Strategic Outcome. Отсутствие Tasks в рабочих статусах достаточно
для формального завершения delivery Goal даже тогда, когда Strategic Outcome
достигнут лишь частично; Scope Reviewer честно называет этот разрыв, но не
превращает его в новую Task, blocker или основание удерживать Goal открытым.
Статусы не доказывают скрытый product outcome, а доступное evidence не
подменяется narrative исполнителей.

### `SR-12` — Никакой скрытой delivery или authority роли

Scope Reviewer не реализует Tasks, не тестирует продукт, не выпускает Release,
не управляет Goal или delivery lifecycle, не переводит Tasks между рабочими
статусами и не принимает production, destructive, access, secret, privacy или
external-recipient decisions. Он анализирует и объясняет scope, а по `SR-05`
может менять только agent-owned planning model при явном intent.

Выявленное действие человека называется необходимым только когда current
evidence подтверждает реальную dependency. Возможная будущая точка контроля не
выдаётся за уже возникший blocker.

Ни Strategic Outcome, ни вывод оптики не расширяют reviewed scope и не создают
скрытое обязательство. Недостающая для общей стратегии работа остаётся
planning gap либо рекомендацией, пока разрешённый planning workflow не внесёт
её в Agent Plan; в Release review такой gap всегда остаётся read-only выводом.

### `SR-13` — Автоматический вход в предзапусковое и live-run ревью

Scope Reviewer автоматически выбирается без обязательного упоминания имени
skill-а в двух классах пользовательских задач:

- человек просит проверить, объяснить или оценить готовность выбранного Task
  Manager плана перед передачей в исполнение;
- человек просит понять, что происходит в активном долгом Issue Grinder / Task
  Manager delivery run: какой результат уже доказан, что ещё выполняется, где
  риск или blocker и требуется ли его участие.

«Автоматически» означает маршрутизацию по смыслу возникшего пользовательского
запроса, а не фоновый запуск по таймеру, после каждого создания плана или при
любом чтении Task. Короткая ссылка вроде «посмотри на неё» достаточна только
когда current conversation и сохранённая run continuity однозначно указывают на
один активный Task Manager scope; иначе Scope Reviewer запрашивает exact выбор и
не угадывает по давности, названию или похожести.

Предзапусковое ревью остаётся read-only Plan review, если человек отдельно не
попросил улучшить план, и само по себе не запускает delivery. Обзор долгого
запуска выполняется как read-only Release review внутри той же пользовательской
Codex task, без создания отдельной task/session. Он использует актуальный Task
Manager snapshot и доступные проверяемые anchors текущего run, сохраняет его
Goal, execution mode, scope, checkpoints и worker ownership и не меняет
lifecycle. Если запрос был добавлением к продолжающемуся запуску, после отчёта
управление возвращается owning Issue Grinder, который продолжает с сохранённого
checkpoint; явная просьба остановить, поставить на паузу или заменить работу
имеет приоритет.

Обычное чтение одной карточки, raw status lookup и произвольная долгая Codex
task без однозначного Task Manager delivery scope не становятся Scope Reviewer
review.

## Изменение Level 1

Новый запрос меняет этот файл только если пользователь меняет обязательный
Scope Reviewer result, invariant или boundary. Просьба улучшить architecture,
упростить процесс, сменить representation, tool или способ проверки при
сохранённых `SR-*` относится к `architecture.md`.
