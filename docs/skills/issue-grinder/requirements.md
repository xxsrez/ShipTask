# Issue Grinder: требования пользователя

Статус: current Level 1, 2026-09-03.

Этот документ — полный current-набор явно сформулированных пользователем
обязательных правил только для `$issue-grinder`. Он определяет, какой результат
должен обеспечивать skill, и является его приоритетной конституцией. Документ
принадлежит пользователю и меняется только по его явному указанию изменить
именно Requirements.

[Architecture](architecture.md) хранит agent-owned current способ достижения
этих требований и все дальнейшие инженерные уточнения. Architecture и будущий
runtime могут конкретизировать требования, но не могут ослабить, заменить или
молча удалить их. Изменение смысла Level 1 требует явного решения пользователя.
Вопросы реализации, не меняющие обязательный результат или границы, агент
решает в Architecture самостоятельно.

Runtime package `issue-grinder/` является компактной смысловой компиляцией
локальных Overview, Requirements и Architecture. Если runtime удалить и
пересобрать из этих трёх самостоятельных документов, новый skill должен быть
примерно эквивалентен по назначению, всем требованиям `IG-*` и выбранной
архитектуре.

Task Manager и Strategic Explainer ниже являются локальными зависимостями
`$issue-grinder`; этот документ не задаёт их собственные требования.

`issue-grinder` получает scope из issue в Task Manager и доводит входящую в него
работу до реализованного и проверенного результата.

## Flow

### `IG-FLOW-01` — Рабочие статусы

`issue-grinder` работает только с issue в статусах `To Do`, `In Progress` и
`In Review`:

- `To Do` по умолчанию входит в scope и означает, что issue нужно реализовать;
- `In Progress` означает, что issue находится в реализации или доработке;
- `In Review` означает, что разработка завершена и issue проверяется.

`Backlog` не входит в работу: `issue-grinder` не реализует находящиеся там issue
и не меняет их статус. После перехода issue в `Done` оно перестаёт интересовать
`issue-grinder`. Отмена issue выполняется пользователем. Все остальные статусы
находятся вне зоны ответственности `issue-grinder`.

### `IG-FLOW-02` — Переходы между статусами

Обычный жизненный цикл issue выглядит так:

1. Перед началом реализации `To Do` переводится в `In Progress`.
2. После завершения разработки `In Progress` переводится в `In Review`.
3. Если проверка выявила дефект, `In Review` возвращается в `In Progress` для
   исправления.
4. Если проверка подтвердила результат, `In Review` переводится в `Done`.

### `IG-FLOW-03` — Комментарии и Strategic Explainer

Каждое изменение статуса, кроме тривиального `To Do → In Progress`, должно
сопровождаться комментарием в соответствующем issue. Комментарий обычным
человеческим языком объясняет, почему новый статус соответствует фактическому
состоянию работы:

- для `In Progress → In Review` — что реализовано и почему результат готов к
  проверке;
- для `In Review → In Progress` — какая проблема обнаружена и почему требуется
  доработка;
- для `In Review → Done` — что проверено и почему результат можно считать
  завершённым.

Сначала проверь активную модель. Если это Astra (`gpt-6-astra`), автоматическая
publication unit не вызывает Strategic Explainer: основной coordinator сам
формулирует текст в native mode, потому что Astra достаточно хорошо делает это
сама. Это условие имеет приоритет над наличием provider-а и ранее выбранным
communication mode и проверяется для каждого нового обычного комментария
и финального комментария об успешном завершении Goal. Подготовка остановки
из-за блокировки Goal, общий blocker-report и объяснения отдельных причин
используют Консультанта по `IG-GOAL-04` и `IG-GOAL-07`, а при ведущей
Astra — самостоятельный разбор и вывод. Strategic Explainer здесь не вызывается. Для остальных
publication units при модели, отличной от Astra, комментарии `issue-grinder`
и финальный комментарий Goal должны проходить через Strategic Explainer, когда
он установлен и доступен. Если Strategic Explainer не установлен или изначально
недоступен, это не блокирует работу: `issue-grinder` пишет требуемый комментарий
самостоятельно. Явный отдельный запрос пользователя к
`$strategic-explainer:strategic-explainer` остаётся самостоятельным вызовом, а
не автоматической зависимостью этого маршрута.

Если установленный Strategic Explainer отклонил обращение потому, что
`issue-grinder` вызвал его неправильно, `issue-grinder` должен понять указанную
причину, исправить вызов и обратиться повторно. Если вызов завершился настоящей
технической ошибкой, `issue-grinder` может остановиться рано и честно сообщить
пользователю об этой ошибке.

### `IG-FLOW-04` — Переоценка решения при подготовке комментария

Подготовка комментария является точкой переоценки, а не формальным отчётом о
заранее принятом решении. Если при формулировании комментария выяснилось, что
ситуация понята не полностью или остаётся существенное действие, необходимое
для обязательного результата текущего issue, `issue-grinder` не публикует
комментарий и не меняет статус по инерции. Он возвращается к работе над issue,
заново оценивает ситуацию и повторяет попытку принять корректное решение.

Необязательное улучшение, дополнительный feature или иная новая работа, не
требуемая текущим scope, не удерживают issue и прогон открытыми сами по себе.

### `IG-FLOW-05` — Смысл блокирующей зависимости

Связь `blocked by` блокирует issue только до реализации необходимого результата.
Если требуемая реализация уже присутствует в ветке, в которой планируется
разрабатывать зависимое issue, блокировка больше не препятствует работе. Статус
блокирующего issue сам по себе не должен удерживать зависимое issue после
появления нужной реализации.

Если позднее в блокирующем результате обнаружен баг или его issue повторно
открыто, это не возвращает зависимое issue автоматически в исходное состояние
блокировки. Затронутую часть результата необходимо повторно проверить.

Ожидание внешней приёмки не останавливает доступную работу scope. Если
разработка завершена, Issue Grinder выполняет все доступные необходимые
проверки, фиксирует оставшуюся внешнюю приёмку и сохраняет issue в `In Review`.
Затем продолжает остальные доступные задачи, включая зависимые, если нужная
реализация присутствует в их рабочей базе и оставшаяся проверка не является
необходимым условием безопасного продолжения. Неизвестный обязательный
контракт или подтверждённый препятствующий дефект сохраняет реальную зависимость;
одного ожидания статуса `Done` для блокировки недостаточно.

Остановка из-за внешней приёмки допустима только после исчерпания всей
самостоятельно выполнимой работы scope. Итоговый blocker-report объединяет
оставшиеся проверки: какие issue ожидают приёмки, что уже проверено, что и
почему агент не может проверить, какое внешнее действие требуется и как
возобновить работу. Если часть разработки действительно недоступна, отчёт
отдельно называет её и причинную зависимость. Непройденная обязательная приёмка
не считается успешной; scope остаётся незавершённым. Это правило не отменяет
явно разрешённый нетерминальный checkpoint Экономичного режима.

### `IG-FLOW-06` — Условие терминального завершения

Работа `issue-grinder` с выбранным scope считается терминально завершённой
только тогда, когда в нём не осталось ни одного issue в `To Do`, `In Progress`
или `In Review`. Наличие issue хотя бы в одном из этих статусов означает, что
scope не завершён.

В `Экономичном` режиме текущая попытка может закончиться полезной контрольной
точкой при незавершённом scope по `IG-MODE-06`. Такая остановка не является
терминальным завершением: статусы issue и Goal остаются правдивыми, а
контрольная точка сохраняется для продолжения того же прогона.

### `IG-FLOW-07` — Консультация при сложном затруднении

Если текущая модель не Astra, доступен Консультант и дальнейшая работа требует
консультации по сложной проблеме, используй Консультанта. Основания: существенная
неопределённость, которую не удалось снять доступными проверками; повторные
неудачные попытки без нового понимания причины; выбор между решениями с
существенными последствиями, для которого не хватает обоснования. Не требуется
сначала ошибиться фиксированное число раз; необходимость консультации оценивает
ведущий агент.

Передай конкретный вопрос, необходимые факты и результаты уже выполненных
проверок. После консультации самостоятельно реализуй решение и проверь
результат. Совет не заменяет проверку и не расширяет полномочия.

Не вызывай Консультанта автоматически из ведущей Astra или для обычной работы
с понятным следующим действием. Если препятствие мешает продолжению и агент
собирается остановиться либо запросить вмешательство пользователя, применяй
цикл консультации из `IG-GOAL-04`. Это относится и к предполагаемой нехватке
доступа или разрешения, недоступности внешнего сервиса и неясности требований.
Кажущаяся очевидность препятствия не освобождает от поиска самостоятельного
выхода. Консультация не становится обязательным этапом каждой задачи.

Исключение из ограничений автоматического вызова — подготовка остановки
из-за блокировки Goal: здесь Консультант обязателен по `IG-GOAL-04`, в том
числе при неизвестном профиле и при предполагаемой зависимости от
доступа, разрешения пользователя или внешнего сервиса. Очевидность причины
для ведущего агента не отменяет этой проверки. При ведущей Astra отдельный
Консультант не вызывается: она сама выполняет разбор по `IG-GOAL-04`.

Это правило действует во всех режимах, включая `Соло`: узкий read-only совет
не передаёт консультанту исполнение, review или acceptance задачи. Явные
ограничения пользователя на субагентов и расходы сохраняют приоритет.

### `IG-FLOW-08` — Итоговый отчёт о расходе

В конце delivery-запуска — при завершении, подтверждённой блокировке или
контрольной точке — Issue Grinder добавляет в ответ пользователю отчёт через
`codex-token-usage-report`, если этот skill доступен в текущей среде. Используется
его актуальный полный формат: все категории и все ненулевые строки моделей
внутри категорий и после общего итога. Краткий ответ не разрешает заменять
таблицу одним суммарным числом.

Отчёт относится только к текущему запуску и его субагентам, с явным периодом
и границей доступной телеметрии. Соседние запуски не включаются. Неполные данные
и неизвестные оценки обозначаются честно; расход ещё не записанного финального
ответа не выдаётся за измеренный.

Это необязательная интеграция по доступности, а не зависимость установки:
Issue Grinder не поставляет, не устанавливает и не копирует этот skill,
его формат или коэффициенты. При отсутствии skill запуск работает без отчёта;
при недоступной или неизолируемой телеметрии кратко указывается ограничение.
Отчёт не публикуется в Task Manager и не блокирует завершение delivery.

## Goal

### `IG-GOAL-01` — Goal только при явном вызове skill

Новый Goal создаётся только при одновременном выполнении двух условий:

1. В scope ожидается больше одного issue.
2. Пользователь явно вызвал skill в prompt, который запустил этот прогон,
   написав `$issue-grinder`.

Если `issue-grinder` загрузился автоматически без явного вызова пользователем,
новый Goal не создаётся независимо от количества issue в scope.

Во время явно вызванного прогона `issue-grinder` ведёт работу внутри
непрерывного цикла Goal. Явный режим сохраняется до завершения этого же прогона,
даже если работа продолжается в следующих turns, проходит через compaction или
восстанавливается после interruption. Старый явный вызов не запускает новый
прогон или новый независимый Goal после завершения исходного прогона.

Полезная нетерминальная контрольная точка `Экономичного` режима может завершить
текущую попытку, но не завершает и не блокирует Goal. Следующее продолжение
возобновляет тот же прогон, Goal и выбранный режим по сохранённой контрольной
точке.

Если scope вырос с одного issue до нескольких уже во время такого прогона,
Goal создаётся в этот момент. Если после создания Goal scope снова сократился
до одного issue, существующий Goal сохраняется.

### `IG-GOAL-02` — Стратегическая цель вместо перечня issue

Перед созданием Goal `issue-grinder` изучает весь текущий фронт issue и
доступный контекст, определяет общую проблему и формулирует ключевой
стратегический результат, ради которого выполняется работа. Эта найденная суть
становится основной целью Goal; Goal не должен быть простым пересказом списка
issue или их статусов.

Goal описывает решаемую проблему, стратегический результат, весь входящий в
scope фронт issue и все необходимые требования, которыми должна
руководствоваться работа. Его смысл нельзя сводить к механическому закрытию
списка мелких issue: отдельные issue являются обязательной декомпозицией и
средствами достижения общей цели, но не заменяют её.

Если scope задан текущим Release, Goal должен быть сфокусирован на успешном
результате всего Release, а не на самом факте перевода входящих в него issue в
терминальные статусы. Эта стратегическая цель служит конституцией прогона,
остаётся видимой и регулярно напоминает, какую общую проблему должен решить
`issue-grinder`.

Стратегический результат является постоянным контекстом исполнения, а не только
текстом при создании Goal. Он направляет выбор frontier, решение внутри каждой
Task, делегирование, integration, review и анализ блокировки. После compaction,
interruption, продолжения и изменения scope этот контекст восстанавливается до
следующего существенного решения. Для прогона без отдельного Goal ту же роль
играет Strategic Outcome текущей Task, её Epic либо всего выбранного scope:
отсутствие платформенного Goal не разрешает исполнять локальную карточку в
отрыве от общего смысла.

При этом Strategic Outcome не является источником новых Requirements, Tasks,
acceptance criteria, проверок или полномочий. Он помогает выбрать способ
выполнения уже существующих обязательств, но не расширяет exact issue contract.

### `IG-GOAL-03` — Условие завершения Goal

Goal не считается завершённым, пока в текущем scope остаётся хотя бы одно issue
в `To Do`, `In Progress` или `In Review`. До выполнения этого условия
`issue-grinder` продолжает цикл Goal. Если все issue покинули эти три статуса,
этого достаточно, чтобы после финальной переоценки считать Goal выполненным.

Нетерминальная контрольная точка `Экономичного` режима не является обходом
этого условия. Она оставляет Goal активным и сохраняет точное незавершённое
состояние для следующего продолжения.

Стратегическая цель задаёт направление работы и не позволяет подменить
достижение результата бесконечной бюрократией вокруг отдельных issue, но не
создаёт второй независимый критерий завершения поверх закрытия всего scope.
Даже известный разрыв между формально завершёнными Tasks и более широким
Strategic Outcome не удерживает Goal открытым и не создаёт новую работу сам по
себе: разрыв отражается в итоговом отчёте и может стать входом отдельного
planning-прогона.

### `IG-GOAL-04` — Цикл переоценки при блокировке

Если `issue-grinder` не может продвигаться по Goal, он сначала честно
анализирует, что произошло, почему работа остановилась и как препятствие можно
устранить наиболее удобным способом.

Перед тем как остановить текущую попытку из-за предполагаемой блокировки Goal,
`issue-grinder` обязательно обращается к отдельному Консультанту во всех
режимах, кроме случая, когда ведущая модель — Astra (`gpt-6-astra`). Ведущая
Astra сама выполняет описанный ниже разбор предпосылок остановки, поиск пути
продолжения и подготовку вывода; отдельного Консультанта она не вызывает.
При неизвестном профиле исключение Astra не применяется. Strategic Explainer
не используется в этой ветке. Для остальных моделей собственное объяснение
не заменяет консультацию: цена ложной остановки важнее экономии на обращении.

Консультант используется для поиска самостоятельного выхода, а не для формального
подтверждения остановки. Одна консультация недостаточна, если остались существенные
непроверенные предположения, перспективные альтернативы или неясность в предложенном
способе продолжения.

Допускаются и ожидаются несколько консультаций по разным существенным вопросам
и уточнения после проверок. Ведущий агент проверяет предложенные варианты,
возвращает результаты Консультанту и продолжает разбор, пока существует обоснованная
возможность продвинуть обязательный результат самостоятельно. Фиксированного
ограничения числа консультаций нет: предотвращение ложной блокировки важнее
экономии на отдельных обращениях.

Каждое повторное обращение должно закрывать конкретный оставшийся пробел либо
учитывать новые факты. Повторение прежнего вопроса без нового основания не является
прогрессом. Консультант остаётся советчиком; исполнение, проверка результата и
решения о полномочиях остаются у ведущего агента.

Если продолжение требует разрешения пользователя, до запроса агент проверяет
техническую осуществимость предлагаемой последовательности доступными разрешёнными
способами. Вывод «нужно разрешение» недостаточен, если неизвестно, позволит ли оно
действительно продолжить работу.

Консультант получает текущий scope, обязательный результат, предполагаемые причины
блокировки, актуальные источники, уже выполненные попытки и границы полномочий.
Его задача — проверить предпосылки остановки, найти пропущенный разрешённый путь
продолжения и подготовить понятный пользователю причинный вывод. Он не должен
принимать блокировку за установленный факт лишь потому, что ведущий агент готов
остановиться. Вывод объясняет, что случилось, что ещё можно сделать, либо почему
агент не может продолжить сам, какое действие требуется и что позволит возобновить
работу.

Ведущий агент проверяет вывод по актуальным источникам и своим полномочиям.
Для ведущей Astra это обязательная повторная проверка собственного разбора;
все следующие требования к продолжению, отчёту и блокировке сохраняются.
Если консультация или эта проверка выявила существенное доступное действие для
обязательного результата текущего scope, `issue-grinder` отменяет предполагаемую
блокировку, выполняет действие и начинает следующую итерацию. Если после доработок
он снова готов остановиться из-за блокировки, новые факты и оставшиеся препятствия
снова проходят консультацию, а при ведущей Astra — самостоятельный разбор.
Совет не заменяет проверку результата и не разрешает
действия за пределами полномочий.

Только если после консультации и проверки самостоятельного продолжения
действительно нет, `issue-grinder` показывает пользователю проверенный вывод
Консультанта, а при ведущей Astra — собственный проверенный вывод, в составе
отчёта и объяснений по `IG-GOAL-07`. Strategic Explainer
не вызывается для переписывания этого вывода. Решение о блокировке остаётся у
ведущего агента и подчиняется ограничениям платформы на изменение статуса Goal.

Когда отдельный Консультант обязателен, его недоступность или явный запрет
пользователя на запуск не считаются
состоявшейся консультацией и не разрешают молча заменить её Strategic Explainer
или native-отчётом. Агент сообщает, что обязательную проверку остановки выполнить
не удалось, сохраняет возобновляемое состояние и не объявляет блокировку Goal
проверенной. Явные ограничения пользователя на субагентов и расходы не обходятся.
Повторный автоматический turn с теми же фактами и уже проверенным выводом не
создаёт новую консультацию или повторную публикацию сам по себе; новая проверка
нужна при существенном изменении фактов, причин или доступных действий.

### `IG-GOAL-05` — Финальный комментарий и последняя переоценка

Когда критерий завершения Goal достигнут, `issue-grinder` готовит финальный
комментарий только для пользователя в чате. При активной Astra
(`gpt-6-astra`) он формулируется native без вызова Strategic Explainer; в
остальных случаях комментарий проходит через Strategic Explainer по правилам
`IG-FLOW-03`. В любом случае он не публикуется в Task Manager.

Подготовка финального комментария запускает ещё одну переоценку результата,
состояния scope и доступных дальнейших действий. Если обнаружились
незавершённая обязательная работа, изменение scope, неполное понимание
существенного результата или следующий шаг, необходимый для текущего scope и
доступный `issue-grinder`, он не завершает Goal, а начинает следующую итерацию
цикла.

Необязательное улучшение, дополнительный hardening, новый возможный feature или
иная работа за пределами обязательного результата текущего scope могут быть
отражены в итоговом отчёте, но сами по себе не создают новую итерацию. Goal
завершается после того, как финальная переоценка не обнаружила существенных
оснований продолжать текущий прогон.

### `IG-GOAL-06` — Прозрачное завершение без несущественной проверки

Если обязательный результат и основной acceptance текущего issue подтверждены,
но отдельную несущественную деталь невозможно проверить, `issue-grinder` может
не превращать эту проверку в бюрократическую блокировку и завершить
соответствующее issue. Это исключение не разрешает выдавать непроведённую
проверку за успешную.

При таком завершении комментарий в issue должен прямо указывать:

- что именно не было проверено;
- почему проверка оказалась недоступна;
- почему этот пробел не опровергает обязательный результат issue и формальное
  завершение текущего scope;
- какая неопределённость или остаточный риск сохраняется.

Тот же нюанс обязательно раскрывается в итоговом отчёте пользователю и, если
был создан Goal, в его финальном комментарии. Комментарий в issue и финальный
комментарий Goal подготавливаются по правилам `IG-FLOW-03`.

### `IG-GOAL-07` — Отдельное объяснение каждой причины блокировки

Если после консультации или самостоятельного разбора ведущей Astra и проверки
вывода блокировка подтверждена, общий blocker-report, подготовленный
Консультантом либо ведущей Astra соответственно, должен
перечислить все актуальные причины, которые реально не дают
`issue-grinder` продолжить текущий scope. Симптом, следствие или дубль
уже названной причины не выдаются за отдельную причину блокировки.

После общего blocker-report `issue-grinder` даёт пользователю подготовленный
Консультантом либо самой ведущей Astra отдельный ответ по каждой из этих причин.
Общий отчёт и эти ответы
проходят проверку ведущим агентом до публикации; Strategic Explainer в их
подготовке не участвует. Каждый такой ответ обычным языком объясняет:

1. почему именно эта причина блокирует обязательный результат активного issue и
   тем самым не позволяет формально завершить текущий scope;
2. почему `issue-grinder` не может устранить её сам: какого фактического
   доступа, полномочия, внешнего решения или состояния ему не хватает;
3. зачем вообще нужен заблокированный шаг, условие или решение, какую роль он
   играет в issue contract и что он даст в контексте общей цели.

Общий blocker-report и все ответы по отдельным причинам образуют один
обязательный terminal handoff. `issue-grinder` не останавливает текущую попытку и
не блокирует Goal, пока весь этот комплект не подготовлен, не проверен и не
показан пользователю. Если детальный разбор хотя бы одной причины выявил
доступный самостоятельный путь, применяются `IG-GOAL-04` и `IG-AUTO-02`:
блокировка отменяется, а работа продолжается.

## Scope

### `IG-SCOPE-01` — Явный scope имеет приоритет

В начале прогона `issue-grinder` должен однозначно понимать свой scope. Явные
уточнения пользователя в текущем prompt имеют приоритет над иным доступным
контекстом и определяют scope этого прогона.

### `IG-SCOPE-02` — Текущий Release по умолчанию для явного вызова

Если пользователь явно вызвал `$issue-grinder`, но prompt, запустивший прогон,
не задаёт scope, skill использует текущий Release, над которым ведётся работа.
В scope входят все соответствующие этому Release issue в `To Do`,
`In Progress` и `In Review`.

`issue-grinder` не должен угадывать текущий Release. Если его невозможно
однозначно определить из доступного контекста, skill останавливается до начала
работы и просит пользователя уточнить scope.

Если skill активировался неявно, текущий Release не подставляется автоматически.
Неявный запуск начинает delivery только при наличии однозначного selector-а
конкретного issue, Release, Project или иного явно ограниченного scope. Если
такого selector-а нет, `issue-grinder` не выполняет изменяющих действий и просит
пользователя уточнить scope.

### `IG-SCOPE-03` — Scope является динамическим

Scope представляет собой актуальный результат выбранного правила отбора, а не
зафиксированный в начале список issue. Во время прогона issue могут быть
добавлены в Release, исключены из него или иным образом перестать
соответствовать выбранному scope.

`issue-grinder` не обязан непрерывно отслеживать такие изменения. Однако если
он обнаружил, что scope изменился, он должен заново оценить его текущий состав,
адаптировать дальнейшую работу и при необходимости изменить стратегию
достижения Goal. Завершение нельзя объявлять на основании устаревшего
стартового списка issue.

## Codex task UI

### `IG-UI-01` — Название новой задачи Codex по возможности

Issue Grinder может не более одного раза попытаться дать новой задаче Codex
короткое и содержательное имя после определения актуального canonical scope.
Для этого приложение должно явно предоставлять метаданные текущей задачи Codex
и безопасную возможность изменить её название. Кроме того, Issue Grinder должен
однозначно подтвердить, что это новая задача с первым пользовательским запросом,
а текущее название является служебной заглушкой каталога.

Переименование остаётся необязательным улучшением интерфейса. Отсутствие функции,
её отложенная загрузка или ошибка не блокируют выполнение. Уже содержательное,
изменённое или неизвестного происхождения название сохраняется. При
неуверенности Issue Grinder не угадывает идентичность задачи. Новое имя строится
только из проверенного scope, начинается с `Issue Grinder ·` и не включает
статус, дату, ветку или другие изменчивые детали.

## Autonomy

### `IG-AUTO-01` — Максимальная автономность только при явном вызове

Режим максимальной автономности включается только тогда, когда пользователь
явно вызвал skill в prompt, запустившем этот прогон, написав `$issue-grinder`.
Явный вызов означает, что агент оставлен работать самостоятельно и должен сам
принимать необходимые решения в пределах scope.

После запуска режим максимальной автономности сохраняется до завершения этого
же прогона, включая следующие turns, compaction и восстановление после
interruption. Он прекращается при terminal результате либо когда пользователь
явно отменил текущий прогон. Явный вызов из старого завершённого прогона не даёт
автономных полномочий новому прогону.

Если `issue-grinder` загрузился автоматически без явного вызова пользователем,
требования этой секции не действуют и не дают агенту дополнительных полномочий.

### `IG-AUTO-02` — Продолжение при наличии доступного действия

В режиме максимальной автономности `issue-grinder` не должен блокироваться,
пока существует действие, которое он может выполнить самостоятельно и которое
существенно продвигает работу к результату, обещанному выбранным режимом. Он сам
ищет и выполняет доступный следующий шаг.

Блокировка допустима только тогда, когда самостоятельное продолжение
действительно невозможно и агент не может найти способ двигаться дальше без
участия пользователя.

Достигнутая по `IG-MODE-06` контрольная точка `Экономичного` режима не является
блокировкой. После получения одного достаточного возобновляемого кандидата
Issue Grinder не обязан бесконечно создавать дополнительные дешёвые варианты,
если они уже не дают существенного ожидаемого продвижения.

### `IG-AUTO-03` — Свобода работы в UAT и других non-production средах

UAT предоставляется Issue Grinder для самостоятельной разработки, экспериментов
и проверки результата. В рамках порученной работы агент может изменять эту среду,
развёртывать и заменять реализации, менять конфигурацию, схему и данные, создавать
и удалять ресурсы, настраивать тестовый доступ и авторизацию, запускать любые
необходимые проверки, воспроизводить сбои и восстанавливать работоспособность.

Эти действия заранее разрешены и не требуют дополнительных подтверждений
пользователя. Разрешение охватывает весь необходимый цикл: подготовку, изменения,
тестирование, исправление неудачных попыток, восстановление и очистку. Агент не
согласовывает отдельно технические шаги внутри этого цикла.

Возможность временно сломать UAT, необходимость пересоздать тестовые ресурсы,
изменить тестовый доступ или удалить тестовые данные не являются основаниями для
остановки и запроса разрешения. Агент самостоятельно выбирает разумные меры
сохранности и восстановления.

Те же послабления действуют для других non-production сред в пределах порученной
работы. На Production эти послабления не распространяются.

### `IG-AUTO-04` — UAT является средой по умолчанию

Если пользователь не уточнил целевую среду, `issue-grinder` всегда работает с
UAT. Агент должен однозначно знать, какая именно среда является UAT для текущего
проекта.

Если определить UAT невозможно, `issue-grinder` останавливается на раннем
этапе до изменений среды и сообщает пользователю, что целевой UAT необходимо
уточнить. Угадывать среду или переходить на Production нельзя.

### `IG-AUTO-05` — Не запрашивать повторное разрешение на уже разрешённую работу

Перед запросом разрешения агент учитывает полномочия, уже предоставленные
пользователем и правилами проекта. Работа с UAT и другими non-production средами
по `IG-AUTO-03` не требует отдельных апрувов на изменения, тестирование, настройку
тестового доступа, восстановление или очистку.

Если конкретное необходимое действие выходит за пределы уже предоставленных
полномочий, агент сначала выполняет всю доступную разрешённую подготовку и
проверяет осуществимость предложенного пути. Затем одним запросом представляет
весь необходимый цикл действий и его существенные последствия, а не согласовывает
последовательные технические шаги по одному.

Полученное разрешение действует на весь согласованный цикл. Смена модели,
инструмента, compaction или возобновление работы не отменяют его. Повторный запрос
допустим только при существенном выходе за согласованные границы; автоматическое
продолжение без новых обстоятельств не повторяет прежний вопрос.

Обязательное подтверждение самой платформы или инструмента агент не обходит,
но не создаёт дополнительных запросов от себя.

Эти послабления не меняют действующих требований для Production.

## Соразмерные проверки

### `IG-VERIFY-01` — Достаточность по результату и риску

Issue Grinder выбирает проверки, достаточные для подтверждения результата и
существенных рисков изменения. Набор определяется влиянием изменения, а не
числом задач, длительностью работы или желанием перестраховаться. Правила
действуют во всех режимах; независимое review, где оно обязательно, сохраняется
и не означает автоматического запуска полного Quality Gate.

### `IG-VERIFY-02` — Гибкие уровни

Различаются проверка изменения, проверка интеграции и полный Quality Gate.
Проходить все уровни последовательно необязательно. Конкретный состав задаёт
проект. Обязательные проверки затронутой безопасности и сохранности данных не
откладываются только ради ускорения.

### `IG-VERIFY-03` — Когда нужен полный Quality Gate

Полный Quality Gate необходим по явному запросу пользователя, при широком или
высокорисковом изменении и для подтверждения готовности кандидата к Production.
Обычная задача, промежуточная публикация в UAT и наличие Release сами по себе
его не требуют. Одна задача также может быть высокорисковой. Дорогую итоговую
проверку проводят на подготовленном кандидате после необходимой реализации и
устранения известных блокирующих дефектов; ранняя проверка конкретного риска
может быть нужна до этого.

### `IG-VERIFY-04` — Промежуточная нестабильность UAT

В ходе разработки допустимы временные регрессии и неполное покрытие проверками,
если это совместимо с назначением среды и текущей работой. Обнаруженные проблемы
устраняются в пределах обязательного результата. Промежуточная публикация не
объявляется полностью принятой; к завершению scope его обязательные свойства
должны быть подтверждены. Задача завершается по своему контракту; оставшаяся
обязательная интеграционная или релизная приёмка остаётся явно учтённой и не
исчезает после закрытия отдельных задач.

### `IG-VERIFY-05` — Применимость и повторное использование

Перед новым запуском Grinder оценивает применимость уже полученных доказательств.
Исправление требует проверки затронутой части и её существенных зависимостей.
Переход между этапами, передача другому агенту и подготовка к Production сами по
себе не требуют повторять успешный полный прогон. Результаты сохраняют истинную
привязку к проверенному кандидату и условиям; повторное использование требует
доказанной применимости. Существенная неизвестность влияния требует расширения
проверки. Повторные сбои требуют пересмотра диагностики, а не автоматического
перезапуска всей матрицы; фиксированного предела числа полных прогонов нет.

### `IG-VERIFY-06` — Действующий Quality Gate перед Production

Готовность к Production требует действующего полного Quality Gate. Достаточно
ранее выполненного полного прогона, если он остаётся применимым к выпускаемому
кандидату. Влияние изменений продукта, сборки, конфигурации, зависимостей и среды
оценивается; необходимые дополнительные проверки выполняются без автоматического
повтора всего набора. Проверки конкретной среды могут оставаться необходимыми.
Доказательства не дают разрешения на публикацию: запрет Production для Issue
Grinder сохраняется; он готовит доказательства для последующего выпуска.

### `IG-VERIFY-07` — Лёгкая адаптация проекта

Проект задаёт состав проверок, условия выбора и правила применимости результатов.
Grinder использует существующие команды, документацию и артефакты, кратко
обосновывает существенные решения без отдельных документов или согласований на
каждый шаг. Skill объясняет, как проекту организовать это описание. Отсутствие
специального профиля само по себе не блокирует работу: агент использует текущие
требования и исследует необходимое, не ослабляя их. Адаптация не даёт полномочий
переписывать пользовательские требования проекта.

## Режимы исполнения

### `IG-MODE-01` — Четыре канонических режима

Issue Grinder поддерживает четыре пользовательских режима исполнения:
`Соло`, `Классический`, `Баланс` и `Экономичный`.

Режим определяет распределение работы между профилями, допустимую
избыточность, глубину проверки и обещание текущего прогона. Он не изменяет
scope, полномочия, требования к правдивости, изоляции изменений и внешним
эффектам.

Во всех четырёх режимах это распределение относится только к execution topology
самого Issue Grinder: агентам, которым он передаёт анализ scope, исследование,
реализацию, тестирование, техническую проверку, выбор кандидата или другое
содержательное delivery-решение. Техническое наличие других агентов в дереве
сессии само по себе не меняет режим и не является его нарушением.

### `IG-MODE-02` — Однократный выбор режима

В начале непрерывного прогона выбирается один канонический режим.

1. Если пользователь явно указал поддерживаемый режим, используется он после проверки допустимости основной сессии по `IG-MODE-20`.
2. Иначе небольшой и средний объём работ исполняется в режиме `Соло`.
3. Обоснованно крупный объём работ исполняется в режиме `Классический`.

Крупный объём включает несколько содержательных направлений, каждое из которых
требует отдельного контекста реализации и проверки, а распределение работы или
независимая проверка дают существенную пользу относительно затрат на
координацию. Агент оценивает содержание выбранного live scope и кратко
обосновывает автовыбор конкретным составом работ.

Количество карточек, их декомпозиция и сложность отдельной задачи сами по себе
не означают крупный объём. Жёсткого порога по числу задач нет. Если оснований
для крупного объёма недостаточно, выбирается `Соло`.

Автовыбор не зависит от основной модели, reasoning effort, квоты или capacity.
`Баланс` и `Экономичный` включаются только явно и сохраняют ограничения
допустимости основной сессии по `IG-MODE-20`. `По умолчанию` означает этот
автовыбор, а не отдельный режим.

Удалённые режимы и их старые имена не разрешают скрытый переход в другой режим.
При явном запросе либо восстановлении такого режима агент сохраняет имеющуюся
работу и запрашивает выбор одного из четырёх поддерживаемых режимов.

Выбранный режим сохраняется до конца того же прогона, включая следующие turns,
compaction, interruption, восстановление и смену основной модели. Автоматически
он повторно не вычисляется. Изменить его может только явная команда
пользователя.

### `IG-MODE-03` — Классический режим

`Классический` является уверенным терминальным режимом с полным управлением и
проверкой результата основным либо нормализованным проверяющим профилем.

- Проверяющий профиль изучает весь live scope, определяет стратегию,
  декомпозицию, зависимости, acceptance и опасные поверхности.
- Существенные продуктовые, архитектурные, межзадачные, миграционные,
  concurrency, security и другие плохо проверяемые решения принимает этот
  профиль.
- Без отдельного выбора пользователя экономичный профиль получает только
  ограниченные самодостаточные пакеты с объективной проверкой и без
  существенного самостоятельного решения.
- Один integration owner объединяет изменения и проверяет точную
  интегрированную версию. Проверяющий профиль проводит итоговое code review и
  проверку результата до терминальной приёмки.
- Любой точный интегрированный кандидат до терминальной приёмки получает
  независимую проверку. Малый или простой scope не отменяет проверяющего: он
  только не требует искусственного дробления проверки на несколько ролей.
- Намеренные конкурирующие реализации одной большой работы по умолчанию не
  создаются. Делегация используется для полезных независимых пакетов и
  независимой проверки.
- Прогон продолжается до терминального результата всего scope либо настоящей
  блокировки.

### `IG-MODE-04` — Баланс

`Баланс` доводит scope до терминального результата при минимальном расходе
Sol и сопоставимом качестве. Основной агент обязательно Luna Max по
`IG-MODE-20`; он владеет координацией, процессами, обычной реализацией,
проверками, локальными исправлениями и интеграцией. Дополнительный
Luna-supervisor только для формального разделения ролей не создаётся.

Sol Extra High (`gpt-5.6-sol`, `reasoning_effort=xhigh`) вызывается за конкретным
решением либо получает целый сложный участок до проверенного результата.
Неоднозначность общего контракта и отсутствие прогресса при разных
содержательных попытках требуют рассмотрения эскалации, а не бесконечного
цикла Luna. Sol не используется для обычных статусов, ожиданий и управления
Luna; передача не превращается в пошаговое консультирование.

Перед терминальной приёмкой каждый точный интегрированный кандидат получает
независимую техническую проверку Sol Extra High по исходным требованиям и
рискам, включая малый scope. Проверяющий не может быть автором кандидата.
Сводка автора не заменяет самостоятельное изучение; применимые результаты
проверок переиспользуются, а существенные пробелы проверяются независимо.
После существенных исправлений проверяется изменённый кандидат.

Контекст передаётся ограниченно, без полного журнала попыток. Один вызванный
владелец возвращает один собранный результат; обычная координация остаётся
на Luna. Оценивается расход дорогого профиля и общий расход при сохранении
качества. Экономия не разрешает ослаблять приёмку. Режим терминальный:
особый нетерминальный выход `Экономичного` ему недоступен.

### `IG-MODE-06` — Экономичный режим

`Экономичный` требует основную сессию Luna Max по `IG-MODE-20`. Дорогой root
как transport/authority оболочка не допускается.

`Экономичный` максимально продвигает scope силами экономичного координатора и
экономичных исполнителей, сводя расход более дефицитного профиля к минимуму. Он
может использовать исследование, реализацию, тесты, self-review, независимую
критику и ограниченный выбор из нескольких вариантов.

Режим минимизирует не только использование дефицитного профиля, но и избыточную
работу экономичных профилей. Текущий экономичный координатор может совмещать
координацию, последовательную реализацию и интеграцию. Отдельный управляющий или
исполнитель не создаётся только ради формального разделения ролей.
Дополнительные исполнители используются при обоснованной пользе от независимой
работы или разделения контекста с учётом стоимости координации и проверки.
Независимый итоговый проверяющий не может быть автором кандидата.

Перед терминальной приёмкой точный кандидат получает независимую проверку
экономичным профилем независимо от размера scope. Если прогон оставляет
resumable checkpoint, проверка может остаться отложенным gate, но её отсутствие
должно быть указано явно и не позволяет объявить результат завершённым.

В отличие от остальных режимов, текущая попытка может закончиться полезным
нетерминальным результатом. В таком случае она обязана оставить:

1. один рекомендуемый точный кандидат;
2. сохранённые изменения с доказанным task ownership;
3. выполненные проверки и их реальные результаты;
4. известные дефекты, неопределённости и отложенные gates;
5. точную точку продолжения того же прогона;
6. правдивые статусы Task Manager и незавершённый Goal.

Работа, реально готовая к проверке, может перейти в `In Review`; неготовая
остаётся `In Progress`. Непроверенный результат нельзя переводить в `Done`, а
незавершённый Goal нельзя объявлять выполненным. Если доступное evidence всё же
достаточно для обычной терминальной приёмки, режим не запрещает завершить scope.

### `IG-MODE-07` — Нормализация профилей

В `Балансе` controller/worker — Luna Max, specialist/reviewer — Sol Extra High.
В `Экономичном` все содержательные роли — Luna Max. Их основная сессия проходит
`IG-MODE-20`; нормализация или role override не обходят этот запрет.
Остальная нормализация ниже относится к `Классическому`.

После выбора многоагентного режима экономичным рабочим профилем является
`gpt-5.6-luna` с `reasoning_effort: max`.

Эта нормализация применяется к режимам с отдельными управляющими,
проверяющими или рабочими ролями. В `Соло` она не заменяет текущую основную
модель и не создаёт supervisor либо worker: единственный исполнитель сохраняет
exact top-level model и effort текущего run.

Если основная модель надёжно считается сильнее экономичного профиля выбранного
режима, основной профиль используется для управления и проверки, а
экономичный — для предусмотренных режимом рабочих ролей. Если основная модель
слабее экономичного профиля или равна ему, управляющий, проверяющий и рабочий
профили схлопываются в экономичный профиль. Основная модель семейства
`gpt-5.6-luna` с effort не выше effort экономичного профиля относится ко
второму случаю.

Если отношение профилей разных семейств не установлено надёжно, Issue Grinder
не объявляет один из них более сильным по догадке и не подменяет основной
профиль. Только в `Классическом` технически неизменяемый корневой агент может оставаться оболочкой, но
содержательные управляющие и рабочие роли выполняются на нормализованном
профиле.

Явная команда пользователя в prompt о модели или reasoning effort всех либо
конкретных ролей имеет приоритет. Сам выбор основной модели при запуске не
является запретом на предусмотренную этим требованием нормализацию.

### `IG-MODE-08` — Безопасная неудача экономичного агента

Экономичный агент не обязан любой ценой доводить рабочий пакет до конца. При
существенной неопределённости он сохраняет уже выполненную работу, затронутые
поверхности, evidence и причину остановки. Дальнейший маршрут зависит от
выбранного режима: пакет может получить проверяющий профиль, targeted rework
той же экономичной сессии или один materially иной восстановительный путь.

Issue Grinder не должен застревать в бесконечной повторной отправке одной
неразрешённой проблемы одинаковым агентам. Неудачные попытки отбрасываются либо
сохраняются как отрицательное evidence; восстановительный кандидат получает
отдельную identity и не смешивается с интегрированным результатом.

### `IG-MODE-09` — Сжатие перед итоговой проверкой

Правила применимости доказательств действуют во всех режимах, включая
самопроверку `Соло`. После изменения результата агент определяет, какие ранее
выполненные проверки сохраняют применимость, а какие требуется повторить.
Учитываются изменения кода, тестов, конфигурации, среды и существенных
зависимостей. Повторная проверка охватывает исправление, затронутые риски и
необходимую интеграционную приёмку. Неизвестность влияния изменения является
основанием расширить проверку.

Полное повторение ранее успешной проверки не требуется исключительно из-за
передачи результата другому агенту или перехода к следующей фазе. Независимый
проверяющий самостоятельно оценивает достаточность и достоверность доказательств,
исследует существенные риски и при необходимости перепроверяет результаты.
Использование существующих доказательств не заменяет независимое суждение.

Массовая экономичная работа не должна превращаться в массовое потребление
проверяющего профиля. Ему передаются один точный кандидат, существенный source
context, принятые решения, выполненные проверки, известные дефекты,
неразрешённые возражения и отрицательное evidence.

Проверяющий профиль самостоятельно читает существенный код и доказательства,
но не обязан изучать полный поток всех неудачных попыток. После material rework
итоговая проверка применяется заново к точному изменённому кандидату.

Сжатие не является голосованием. Для каждого существенного finding сохраняются
evidence и disposition `исправлено | опровергнуто | передано на решение`;
неразрешённое замечание нельзя потерять среди нескольких общих одобрений.

### `IG-MODE-10` — Явное переключение режима

Пользователь может явно изменить режим незавершённого прогона. Переключение
происходит через безопасную контрольную точку: уже созданная работа сохраняется,
активные авторы не дублируются, а новый режим применяется к последующей
диспетчеризации.

Без явной команды пользователя автоматического переключения между режимами
нет. Само переключение не изменяет scope, environment или authority.

### `IG-MODE-11` — Режим «Соло»

`Соло` является терминальным режимом с одним
исполнителем Issue Grinder. Весь выбранный scope на каждом turn выполняет
фактически текущая основная модель с текущим reasoning effort. Issue Grinder не
передаёт свою содержательную работу отдельным supervisor, worker, scout, critic,
verifier, judge, reducer, альтернативным кандидатам или отдельному проверяющему
профилю и не заменяет текущую модель автоматически другим профилем.

Количество issue не определяет этот режим. Пользователь может явно выбрать
`Соло`, `single`, `сингл`, «одним агентом», «без субагентов» или другую
однозначную свободную формулировку как для одного issue, так и для Release,
Project или другого scope с любым числом issue. При отсутствии явного выбора
применяется автовыбор по `IG-MODE-02`.

В `Соло` текущая модель:

- полностью анализирует live scope, зависимости, acceptance и риски;
- берёт в содержательное исполнение только один issue или рабочий пакет за раз
  и продвигает scope последовательно;
- самостоятельно реализует, интегрирует, проверяет и проводит self-review
  точного результата;
- использует объективные проверки и evidence, не считая собственную уверенность
  независимым доказательством;
- продолжает run до терминального результата всего scope либо настоящей
  блокировки и не получает право на нетерминальный checkpoint
  `Экономичного` режима.

Goal, Task Manager lifecycle, startup recovery, scope, authority, environment и
требования к правдивости остаются общими. Для scope с несколькими issue `Соло`
не отменяет Goal, когда он требуется по `IG-GOAL-01`. Отдельный Strategic
Explainer или другой сервисный агент допускается по `IG-MODE-12`: он не
становится вторым исполнителем Issue Grinder, пока получает только собственный
семантический запрос и не выполняет delivery-работу выбранного scope.

### `IG-MODE-12` — Граница execution topology режима

Ограничения и обещания каждого режима о числе, профилях и ролях агентов
применяются только к агентам execution topology Issue Grinder. В неё входит
основной агент, на котором исполняется skill, и любой потомок, которому Issue
Grinder передал хотя бы часть анализа scope, исследования, реализации,
тестирования, технического review, выбора или сокращения кандидатов, интеграции
либо другого решения, непосредственно определяющего delivery-результат.

Агент может сам быть создан внешним controller-ом: такой предок не становится
участником topology режима. Аналогично отдельный semantic provider, включая
Strategic Explainer, внутренний агент connector-а или другого явно применимого
skill, остаётся за границей topology режима, если выполняет только собственный
ограниченный interface и не получает работу Issue Grinder. Реализация provider-а
через subagent, task или иной transport не превращает его автоматически в
worker выбранного режима.

Эта граница едина для `Соло`, `Классического` и `Экономичного`. В частности:

- `Соло` сохраняет ровно одного исполнителя Issue Grinder, но не запрещает
  сервисные agent-backed interfaces;
- routing и profile requirements остальных режимов применяются к их
  содержательным execution roles, а не к внутренним агентам внешнего provider-а;
- Консультант по `IG-FLOW-07` и `IG-GOAL-04` остаётся сервисным советчиком:
  он может читать источники и проверять предпосылки остановки, но не получает
  исполнение, техническую приёмку или право решать, блокировать ли Goal;
- остальные service agents не получают права анализировать или изменять source,
  реализовывать scope, запускать его техническую приёмку, выбирать candidate
  либо принимать lifecycle decision. Если он фактически делает такую работу,
  он становится execution agent и обязан соответствовать выбранному режиму;
- явное требование пользователя «вообще не запускать никаких субагентов» сильнее
  этой границы и запрещает также сервисный transport. Сам выбор режима `Соло`
  такого глобального запрета не создаёт.

### `IG-MODE-19` — Непрерывность инструментальной работы

Для каждого запущенного длительного процесса сохраняются проверяемый кандидат,
владелец, состояние и способ получить итоговый результат либо продолжить
ожидание. Пока результат ещё доступен, продолжение работы не должно запускать
процесс заново исключительно из-за потери его состояния при передаче между
шагами или агентами.

Независимые инструментальные операции разрешается выполнять параллельно при
отсутствии конфликтующих изменений, общих эффектов и ограничений среды.
В `Соло` такая параллельность остаётся внутри текущего рабочего пакета: она не
создаёт дополнительных исполнителей и не разрешает одновременное содержательное
выполнение нескольких пакетов.

### `IG-MODE-20` — Обязательная основная сессия Luna Max

`Баланс` и `Экономичный` запускаются и продолжаются только если фактический
основной агент имеет exact `model=gpt-5.6-luna` и `reasoning_effort=max`.
Другой effort, другая модель или неизвестный профиль означают отказ от
исполнения выбранного режима с понятным указанием требуемого профиля.

Проверка предшествует созданию Goal, изменениям Task Manager/файлов и dispatch
исполнителей; при продолжении и явном переключении проверяется текущий, а не
только первоначальный профиль. Режим не подменяется автоматически; запрещены
дорогая оболочка, Luna-supervisor вместо подходящего root и скрытое изменение
настроек основной сессии. Существующая работа сохраняется. Явный role override
не отменяет требование к основному агенту. Чистая справка доступна на любой модели.

Сохранённый старый `balance` не считается новым режимом по одному имени:
нужна подтверждённая версия контракта либо явный переход с сохранением работы.

## Справка

### `IG-HELP-01` — Краткая справка о режимах

По запросу пользователя Issue Grinder кратко объясняет четыре канонических
режимов, автовыбор по `IG-MODE-02` и существенные различия,
достаточные для осознанного явного выбора другого режима. Чистый справочный
запрос не запускает delivery, не разрешает Task Manager scope, не создаёт Goal,
не обращается к Task Manager и не вызывает субагентов.

## Multi-agent

### `IG-MA-01` — Делегация только полезной независимой работы

`issue-grinder` использует execution-субагентов, когда работу можно разделить минимум на
два действительно полезных независимых рабочих пакета либо выбранный режим
оправдывает независимых критиков или проверяющих. Большое количество issue или свободных слотов само по
себе не является достаточным основанием для делегации. `Соло` является явным
исключением: в нём эти условия не запускают execution-субагентов, а вся работа
Issue Grinder выполняется последовательно текущей моделью. Сервисные интерфейсы
не относятся к этой делегации по `IG-MODE-12`.

При выборе делегации учитывается ожидаемая польза вместе со стоимостью
постановки, передачи контекста, ожидания, интеграции и проверки. Наличие
подходящей модели или свободного исполнителя само по себе не требует делегации.
В `Классическом` простой пакет может выполнить основной профиль, если передача
не даёт ожидаемой экономии; обязательная независимая проверка сохраняется.
Эта оценка не требует отдельного расчётного отчёта для каждого пакета.

### `IG-MA-02` — Разделение по классам изменений

Перед делегацией `issue-grinder` группирует работу по затрагиваемым модулям,
файлам, схемам, генерируемым артефактам и другому общему изменяемому состоянию.
Обычные пакеты с пересекающимися или конфликтующими поверхностями записи не
выполняются параллельно.

### `IG-MA-03` — Готовность зависимостей

Параллельно запускаются только рабочие пакеты, которые не зависят от ещё не
реализованного результата другого пакета. Появление готовой зависимости
открывает возможность заново оценить параллельную работу.

### `IG-MA-04` — Адаптивная параллельность

Количество субагентов определяется реальной шириной независимой работы,
доступными ресурсами и стоимостью последующей интеграции и проверки.
`issue-grinder` не создаёт фиктивные пакеты только ради использования свободных
слотов или достижения заданного уровня параллельности. В `Соло` количество
execution-субагентов равно нулю, а одновременно содержательно исполняется
не больше одного пакета. Сервисные агенты в этот счёт не входят.

### `IG-MA-05` — Один владелец интеграции

Ровно один операционный координатор остаётся владельцем Goal, изменений в Task
Manager, общего интегрированного результата и решения о его окончательной
проверке. Только назначенный integration owner объединяет результаты
субагентов. Профиль этих ролей определяется выбранным режимом и
`IG-MODE-07`, но смена профиля не создаёт второго владельца. В `Соло` текущая
модель одновременно является единственным coordinator, author, integration
owner и self-reviewer; отдельных владельцев или исполнителей не создаётся.
В `Экономичном` текущий Luna-координатор также может совмещать авторство и
интеграцию; независимая итоговая проверка остаётся отдельной ролью неавтора.

### `IG-MA-06` — Изоляция авторов изменений

Каждый субагент, который изменяет код параллельно с другими авторами, до первой
записи получает отдельный Git worktree и отдельную `feature branch`,
привязанные к его конкретному рабочему пакету или issue.

### `IG-MA-07` — Исключительное владение worktree

Один Git worktree с правом записи одновременно принадлежит только одному
автору. Субагент не изменяет интеграционную ветку, чужой worktree или ветку
другого рабочего пакета.

### `IG-MA-08` — Read-only роли без отдельного worktree

Субагентам, которые только исследуют состояние или проверяют результат и не
изменяют файлы, отдельный worktree не требуется. Такие роли можно использовать
параллельно даже тогда, когда безопасна только одна полоса записи.

### `IG-MA-09` — Контракт рабочего пакета

Каждый субагент получает ограниченный scope, принадлежащие ему поверхности,
необходимые исходные данные, существенные ограничения, ожидаемый результат и
способ его проверки. Пакет также передаёт Strategic Outcome всего scope,
объясняет вклад конкретного issue или пакета, отличает применимые Human
Requirements от Agent Plan и сохраняет exact локальную границу. Этот контекст
направляет решение субагента, но не разрешает ему придумывать новые требования,
работу или критерии завершения.

### `IG-MA-10` — Проверка интегрированного результата

Отчёт субагента и успешные проверки в его изолированном worktree не доказывают
общий результат. После объединения изменений основной агент проверяет точную
интегрированную версию.

### `IG-MA-11` — Повторная диспетчеризация

После завершения или блокировки рабочего пакета, изменения scope либо появления
готовой зависимости основной агент заново оценивает доступную независимую
работу, состав субагентов и степень полезной параллельности.

### `IG-MA-12` — Обнаружение и продолжение существующей работы

В начале каждого прогона, до создания новой ветки, worktree или повторной
реализации, `issue-grinder` должен обнаружить уже существующую работу в
repository, которая может относиться к текущему scope. В проверку входят как
минимум существующие worktree, ветки, коммиты, staged, unstaged и untracked
изменения, а также доступные контрольные точки незавершённых рабочих пакетов.

Если существующий артефакт однозначно связан с issue или рабочим пакетом
текущего scope и прежний автор остановлен, `issue-grinder` обязан подхватить его
фактическое состояние и продолжить эту работу. Наличие только ветки без
активного worktree, незакоммиченных изменений или частично выполненной
реализации не является основанием начать ту же работу заново, создать
параллельную замену либо проигнорировать уже полученный результат.

Это правило запрещает случайное дублирование.

Если прежний автор ещё активен, продолжение координируется через существующего
владельца без второго параллельного автора. Если происхождение или связь
артефакта со scope неоднозначны, `issue-grinder` сохраняет его, не присваивает
себе, не очищает и не объединяет молча и сначала разрешает неоднозначность.
Одновременно писать в один worktree двум авторам запрещено. Несвязанные
пользовательские изменения должны быть сохранены и не становятся частью scope
автоматически.

### `IG-MA-13` — Приоритет пользовательского профиля

Если пользователь в prompt явно выбрал модель или уровень рассуждений для всех
либо отдельных ролей, этот выбор имеет приоритет и не подменяется молча. Выбор
основной модели при запуске не определяет автовыбор по `IG-MODE-02`
и не переопределяет явный выбор пользователя или сохранённый режим. После выбора многоагентного
режима основная модель является входом нормализации профилей по `IG-MODE-07`, а
не отдельным запретом на неё, кроме обязательного ограничения `IG-MODE-20`. В `Соло` отдельных ролей нет: единственным
профилем исполнения остаются exact model и effort фактически текущего основного
агента. Смена top-level model или effort при продолжении не меняет сохранённый
mode `Соло`, но следующую работу выполняет уже новый current profile без
создания replacement subagent. Противоречивую команду одновременно использовать
другой role profile и не создавать субагентов нельзя разрешать скрытой
подменой.

### `IG-MA-14` — Классическая экономичная полоса

В `Классическом` режиме без отдельного пользовательского выбора
`gpt-5.6-luna` с `reasoning_effort: max` используется только для рабочего
пакета, который одновременно:

- является автономным, ограниченным и самодостаточным;
- имеет ясные входные данные, ожидаемый результат и критерии проверки;
- владеет непересекающимися поверхностями;
- даёт объективно проверяемый результат;
- не требует существенного продуктового, творческого, архитектурного или
  межзадачного решения;
- не несёт существенного риска и не зависит от непредсказуемого состояния
  среды или инструментов.

Маленький diff, небольшое количество файлов или внешне механическая работа сами
по себе не делают пакет простым.

### `IG-MA-15` — Профильная маршрутизация режимов

В `Классическом` режиме пакеты, которые не соответствуют `IG-MA-14`, выполняет
основной либо нормализованный проверяющий профиль. В `Балансе` сложные пакеты и независимую итоговую проверку выполняет Sol Extra High,
а координацию и обычную работу — Luna Max. В
`Экономичном` режиме содержательные coordinator и worker roles
по умолчанию используют экономичный профиль. В `Соло` profile routing не
применяется: весь scope последовательно выполняет текущий основной профиль.

Конкретный маршрут всегда учитывает `IG-MODE-07`, поэтому схлопнутые профили не
симулируют несуществующее разделение на сильную и слабую модели.

### `IG-MA-16` — Передача незавершённого экономичного пакета

Если Luna обнаружила неоднозначность, конфликт контекста или требований,
неожиданное состояние среды или инструментов, необходимость расширить scope
либо невозможность доказать результат, она не маскирует проблему и не продолжает
неограниченные изменяющие действия. Она фиксирует уже выполненную работу,
затронутые поверхности, доступные доказательства и оставшуюся неопределённость.

Дальнейший маршрут определяется режимом: проверяющий профиль может продолжить
пакет, а `Экономичный` может сохранить нетерминальную контрольную точку.
Повторять ту же попытку без нового подхода, evidence или изменившегося состояния
запрещено. В `Соло` пакет не передаётся другому агенту: текущая модель использует
новый безопасный подход или evidence, продолжает следующий доступный шаг либо
проходит обычный terminal blocker gate.

### `IG-MA-17` — Штатная доступность выбранных профилей

Требования к режимам описывают штатное исполнение и исходят из доступности
профилей, предусмотренных выбранной topology. Отдельная политика автоматической
замены недоступной Luna, смены режима либо перераспределения квоты не является
частью требований Issue Grinder.

### `IG-MA-18` — Strategic Explainer вне model routing рабочих пакетов

Профиль Strategic Explainer не выбирается правилами Luna для рабочих
субагентов. Strategic Explainer самостоятельно управляет своим исполнением
через собственный интерфейс. Этот interface доступен во всех четырёх режимах,
включая `Соло`, и не входит в execution topology режима по `IG-MODE-12`, кроме
автоматической ветки Astra (`gpt-6-astra`): там provider не вызывается, а
coordinator пишет native text. Coordinator в provider-ветке передаёт ему только
publication request и всегда сохраняет владение фактами, reflection, lifecycle
decision и самой публикацией.

### `IG-MA-19` — Один владелец волны и ограниченная координация

Во всех режимах, кроме `Соло`, каждая многоагентная рабочая или проверочная
волна имеет ровно одного владельца, видимого её родительскому координатору.
В `Классическом` и `Балансе` это владелец независимой проверки, в `Экономичном` —
текущий Luna-контроллер либо вызванный им Luna-supervisor. Дополнительный
supervisor не обязателен, если текущий Luna-контроллер сам выполняет работу.

На малом scope владелец проверки проводит её сам. На большом scope reviewer
`Классического` может создать ограниченные read-only проверки по независимым
поверхностям риска. Родителю возвращается один объединённый finding ledger
с точным кандидатом, отрицательным evidence и disposition существенных замечаний.

Нормальный успешный жизненный цикл нового прямого владельца содержит одну
проверку маршрута по заранее разрешённому guard, один dispatch и одно событийное
ожидание до результата, запроса внимания или установленного deadline. Поиск
guard, чтение его справки, периодический status polling, повторные `list`,
пустые nudges и другие ходы при неизменившемся состоянии не входят в нормальный
путь.

После material rework тот же владелец и та же проверочная сессия получают точный
изменённый кандидат и проходят ещё одно событийное ожидание. Новый проверяющий
создаётся только если прежний недоступен, потерял независимость либо
изменившийся scope требует другого контракта.

Ожидание ограничено deadline проверяющего и общим потолком прогона. При
истечении срока владелец возвращает полный либо частичный finding ledger.
Незавершённая проверка блокирует терминальную приёмку, но в `Экономичном` может
быть честно сохранена как отложенный gate resumable checkpoint.
