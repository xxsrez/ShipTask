# Issue Grinder: требования пользователя

Статус: current Level 1, 2026-08-28.

Этот документ — полный current-набор явно сформулированных пользователем
обязательных правил только для `$issue-grinder`. Он определяет, какой результат
должен обеспечивать skill, и является его приоритетной конституцией.

[Architecture](architecture.md) хранит agent-owned current способ достижения
этих требований и все дальнейшие инженерные уточнения. Architecture и будущий
runtime могут конкретизировать требования, но не могут ослабить, заменить или
молча удалить их. Изменение смысла Level 1 требует явного решения пользователя.
Вопросы реализации, не меняющие обязательный результат или границы, агент
решает в Architecture самостоятельно.

Task Manager и Strategic Explainer ниже являются локальными зависимостями
`$issue-grinder`; этот документ не задаёт их собственные требования.

`issue-grinder` получает scope из issue в Task Manager и доводит входящую в него
работу до реализованного и проверенного результата.

## Flow

### `IG-FLOW-01` — Рабочие статусы

`issue-grinder` работает только с issue в статусах `To Do`, `In Progress` и
`In Review`:

- `To Do` по умолчанию входит в scope и означает, что issue нужно реализовать;
- `In Progress` означает, что issue находится в реализации или доработке;
- `In Review` означает, что разработка завершена и issue проверяется.

`Backlog` не входит в работу: `issue-grinder` не реализует находящиеся там issue
и не меняет их статус. После перехода issue в `Done` оно перестаёт интересовать
`issue-grinder`. Отмена issue выполняется пользователем. Все остальные статусы
находятся вне зоны ответственности `issue-grinder`.

### `IG-FLOW-02` — Переходы между статусами

Обычный жизненный цикл issue выглядит так:

1. Перед началом реализации `To Do` переводится в `In Progress`.
2. После завершения разработки `In Progress` переводится в `In Review`.
3. Если проверка выявила дефект, `In Review` возвращается в `In Progress` для
   исправления.
4. Если проверка подтвердила результат, `In Review` переводится в `Done`.

### `IG-FLOW-03` — Комментарии и Strategic Explainer

Каждое изменение статуса, кроме тривиального `To Do → In Progress`, должно
сопровождаться комментарием в соответствующем issue. Комментарий обычным
человеческим языком объясняет, почему новый статус соответствует фактическому
состоянию работы:

- для `In Progress → In Review` — что реализовано и почему результат готов к
  проверке;
- для `In Review → In Progress` — какая проблема обнаружена и почему требуется
  доработка;
- для `In Review → Done` — что проверено и почему результат можно считать
  завершённым.

Все комментарии `issue-grinder` и финальный комментарий Goal должны проходить
через Strategic Explainer, когда он установлен и доступен. Если Strategic
Explainer не установлен или изначально недоступен, это не блокирует работу:
`issue-grinder` пишет требуемый комментарий самостоятельно.

Если установленный Strategic Explainer отклонил обращение потому, что
`issue-grinder` вызвал его неправильно, `issue-grinder` должен понять указанную
причину, исправить вызов и обратиться повторно. Если вызов завершился настоящей
технической ошибкой, `issue-grinder` может остановиться рано и честно сообщить
пользователю об этой ошибке.

### `IG-FLOW-04` — Переоценка решения при подготовке комментария

Подготовка комментария является точкой переоценки, а не формальным отчётом о
заранее принятом решении. Если при формулировании комментария выяснилось, что
ситуация понята не полностью или остаётся существенное действие, необходимое
для обязательного результата текущего issue, `issue-grinder` не публикует
комментарий и не меняет статус по инерции. Он возвращается к работе над issue,
заново оценивает ситуацию и повторяет попытку принять корректное решение.

Необязательное улучшение, дополнительный feature или иная новая работа, не
требуемая текущим scope, не удерживают issue и прогон открытыми сами по себе.

### `IG-FLOW-05` — Смысл блокирующей зависимости

Связь `blocked by` блокирует issue только до реализации необходимого результата.
Если требуемая реализация уже присутствует в ветке, в которой планируется
разрабатывать зависимое issue, блокировка больше не препятствует работе. Статус
блокирующего issue сам по себе не должен удерживать зависимое issue после
появления нужной реализации.

Если позднее в блокирующем результате обнаружен баг или его issue повторно
открыто, это не возвращает зависимое issue автоматически в исходное состояние
блокировки. Затронутую часть результата необходимо повторно проверить.

### `IG-FLOW-06` — Условие завершения прогона

Работа `issue-grinder` с выбранным scope считается завершённой только тогда,
когда в нём не осталось ни одного issue в `To Do`, `In Progress` или
`In Review`. Наличие issue хотя бы в одном из этих статусов означает, что
прогон не завершён.

## Goal

### `IG-GOAL-01` — Goal только при явном вызове skill

Новый Goal создаётся только при одновременном выполнении двух условий:

1. В scope ожидается больше одного issue.
2. Пользователь явно вызвал skill в prompt, который запустил этот прогон,
   написав `$issue-grinder`.

Если `issue-grinder` загрузился автоматически без явного вызова пользователем,
новый Goal не создаётся независимо от количества issue в scope.

Во время явно вызванного прогона `issue-grinder` ведёт работу внутри
непрерывного цикла Goal. Явный режим сохраняется до завершения этого же прогона,
даже если работа продолжается в следующих turns, проходит через compaction или
восстанавливается после interruption. Старый явный вызов не запускает новый
прогон или новый независимый Goal после завершения исходного прогона.

Если scope вырос с одного issue до нескольких уже во время такого прогона,
Goal создаётся в этот момент. Если после создания Goal scope снова сократился
до одного issue, существующий Goal сохраняется.

### `IG-GOAL-02` — Стратегическая цель вместо перечня issue

Перед созданием Goal `issue-grinder` изучает весь текущий фронт issue и
доступный контекст, определяет общую проблему и формулирует ключевой
стратегический результат, ради которого выполняется работа. Эта найденная суть
становится основной целью Goal; Goal не должен быть простым пересказом списка
issue или их статусов.

Goal описывает решаемую проблему, стратегический результат, весь входящий в
scope фронт issue и все необходимые требования, которыми должна
руководствоваться работа. Его смысл нельзя сводить к механическому закрытию
списка мелких issue: отдельные issue являются обязательной декомпозицией и
средствами достижения общей цели, но не заменяют её.

Если scope задан текущим Release, Goal должен быть сфокусирован на успешном
результате всего Release, а не на самом факте перевода входящих в него issue в
терминальные статусы. Эта стратегическая цель служит конституцией прогона,
остаётся видимой и регулярно напоминает, какую общую проблему должен решить
`issue-grinder`.

### `IG-GOAL-03` — Условие завершения Goal

Goal не считается завершённым, пока в текущем scope остаётся хотя бы одно issue
в `To Do`, `In Progress` или `In Review`. До выполнения этого условия
`issue-grinder` продолжает цикл Goal. Если все issue покинули эти три статуса,
этого достаточно, чтобы после финальной переоценки считать Goal выполненным.

Стратегическая цель задаёт направление работы и не позволяет подменить
достижение результата бесконечной бюрократией вокруг отдельных issue, но не
создаёт второй независимый критерий завершения поверх закрытия всего scope.

### `IG-GOAL-04` — Цикл переоценки при блокировке

Если `issue-grinder` не может продвигаться по Goal, он сначала честно
анализирует, что произошло, почему работа остановилась и как препятствие можно
устранить наиболее удобным способом.

Если Strategic Explainer доступен, `issue-grinder` использует его для
подготовки подробного и понятного пользователю объяснения: что случилось и как
это можно решить. Если Strategic Explainer отсутствует или изначально
недоступен, `issue-grinder` формулирует объяснение самостоятельно. Ошибки
обращения к установленному Strategic Explainer обрабатываются по правилам
`IG-FLOW-03`.

Подготовка объяснения одновременно является повторной проверкой доступного пути
вперёд. Если в ходе анализа обнаружилось действие, которое `issue-grinder`
может выполнить самостоятельно, он не блокирует Goal, выполняет это действие и
начинает следующую итерацию цикла. Пользователь получает blocker-report, а Goal
признаётся заблокированным, только когда самостоятельного продолжения
действительно нет и требуется участие пользователя.

### `IG-GOAL-05` — Финальный комментарий и последняя переоценка

Когда критерий завершения Goal достигнут, `issue-grinder` готовит финальный
комментарий только для пользователя в чате. Этот комментарий проходит через
Strategic Explainer по правилам `IG-FLOW-03` и не публикуется в Task Manager.

Подготовка финального комментария запускает ещё одну переоценку результата,
состояния scope и доступных дальнейших действий. Если обнаружились
незавершённая обязательная работа, изменение scope, неполное понимание
существенного результата или следующий шаг, необходимый для текущего scope и
доступный `issue-grinder`, он не завершает Goal, а начинает следующую итерацию
цикла.

Необязательное улучшение, дополнительный hardening, новый возможный feature или
иная работа за пределами обязательного результата текущего scope могут быть
отражены в итоговом отчёте, но сами по себе не создают новую итерацию. Goal
завершается после того, как финальная переоценка не обнаружила существенных
оснований продолжать текущий прогон.

### `IG-GOAL-06` — Прозрачное завершение без несущественной проверки

Если общая стратегическая цель достигнута, но отдельную несущественную деталь
невозможно проверить, `issue-grinder` может не превращать эту проверку в
бюрократическую блокировку и завершить соответствующее issue. Это исключение
не разрешает выдавать непроведённую проверку за успешную.

При таком завершении комментарий в issue должен прямо указывать:

- что именно не было проверено;
- почему проверка оказалась недоступна;
- почему этот пробел не препятствует достижению общей стратегической цели;
- какая неопределённость или остаточный риск сохраняется.

Тот же нюанс обязательно раскрывается в итоговом отчёте пользователю и, если
был создан Goal, в его финальном комментарии. Комментарий в issue и финальный
комментарий Goal подготавливаются по правилам `IG-FLOW-03`.

## Scope

### `IG-SCOPE-01` — Явный scope имеет приоритет

В начале прогона `issue-grinder` должен однозначно понимать свой scope. Явные
уточнения пользователя в текущем prompt имеют приоритет над иным доступным
контекстом и определяют scope этого прогона.

### `IG-SCOPE-02` — Текущий Release по умолчанию для явного вызова

Если пользователь явно вызвал `$issue-grinder`, но prompt, запустивший прогон,
не задаёт scope, skill использует текущий Release, над которым ведётся работа.
В scope входят все соответствующие этому Release issue в `To Do`,
`In Progress` и `In Review`.

`issue-grinder` не должен угадывать текущий Release. Если его невозможно
однозначно определить из доступного контекста, skill останавливается до начала
работы и просит пользователя уточнить scope.

Если skill активировался неявно, текущий Release не подставляется автоматически.
Неявный запуск начинает delivery только при наличии однозначного selector-а
конкретного issue, Release, Project или иного явно ограниченного scope. Если
такого selector-а нет, `issue-grinder` не выполняет изменяющих действий и просит
пользователя уточнить scope.

### `IG-SCOPE-03` — Scope является динамическим

Scope представляет собой актуальный результат выбранного правила отбора, а не
зафиксированный в начале список issue. Во время прогона issue могут быть
добавлены в Release, исключены из него или иным образом перестать
соответствовать выбранному scope.

`issue-grinder` не обязан непрерывно отслеживать такие изменения. Однако если
он обнаружил, что scope изменился, он должен заново оценить его текущий состав,
адаптировать дальнейшую работу и при необходимости изменить стратегию
достижения Goal. Завершение нельзя объявлять на основании устаревшего
стартового списка issue.

## Autonomy

### `IG-AUTO-01` — Максимальная автономность только при явном вызове

Режим максимальной автономности включается только тогда, когда пользователь
явно вызвал skill в prompt, запустившем этот прогон, написав `$issue-grinder`.
Явный вызов означает, что агент оставлен работать самостоятельно и должен сам
принимать необходимые решения в пределах scope.

После запуска режим максимальной автономности сохраняется до завершения этого
же прогона, включая следующие turns, compaction и восстановление после
interruption. Он прекращается при terminal результате либо когда пользователь
явно отменил текущий прогон. Явный вызов из старого завершённого прогона не даёт
автономных полномочий новому прогону.

Если `issue-grinder` загрузился автоматически без явного вызова пользователем,
требования этой секции не действуют и не дают агенту дополнительных полномочий.

### `IG-AUTO-02` — Продолжение при наличии доступного действия

В режиме максимальной автономности `issue-grinder` не должен блокироваться,
пока существует действие, которое он может выполнить самостоятельно и которое
позволяет продвинуть работу. Он сам ищет и выполняет доступный следующий шаг.

Блокировка допустима только тогда, когда самостоятельное продолжение
действительно невозможно и агент не может найти способ двигаться дальше без
участия пользователя.

### `IG-AUTO-03` — Production запрещён, непроизводственные среды разрешены

`issue-grinder` не трогает Production. Явный вызов skill не снимает этот
запрет.

UAT, staging и другие непроизводственные среды доступны `issue-grinder` для
любых необходимых действий в пределах scope. Дополнительное разрешение на
обычные действия в этих средах не требуется, даже если среда публична. Сам по
себе публичный доступ к UAT не является основанием остановиться или запросить
разрешение пользователя.

### `IG-AUTO-04` — UAT является средой по умолчанию

Если пользователь не уточнил целевую среду, `issue-grinder` всегда работает с
UAT. Агент должен однозначно знать, какая именно среда является UAT для текущего
проекта.

Если определить UAT невозможно, `issue-grinder` останавливается на раннем
этапе до изменений среды и сообщает пользователю, что целевой UAT необходимо
уточнить. Угадывать среду или переходить на Production нельзя.

### `IG-AUTO-05` — Исключительный запрос разрешения

В режиме максимальной автономности вопрос о разрешении допустим только в
крайнем случае, когда агент видит действительно очень высокий риск
безопасности. Обычный риск работы с UAT, включая публичный UAT, не является
достаточным основанием прерывать работу.

Если разрешение всё же необходимо запросить, `issue-grinder` предлагает
пользователю селектор с тремя вариантами:

- `Да` — разрешить текущее действие;
- `Нет` — не разрешать текущее действие;
- `Да всегда` — разрешить текущую и последующие операции той же категории.

При выборе `Да всегда` `issue-grinder` сам определяет осмысленную категорию
разрешения и сохраняет её в project memory, чтобы впредь не задавать такой же
вопрос для этого проекта.

## Multi-agent

### `IG-MA-01` — Делегация только полезной независимой работы

`issue-grinder` использует субагентов, когда работу можно разделить минимум на
два действительно полезных и независимых рабочих пакета. Большое количество
issue само по себе не является достаточным основанием для делегации.

### `IG-MA-02` — Разделение по классам изменений

Перед делегацией `issue-grinder` группирует работу по затрагиваемым модулям,
файлам, схемам, генерируемым артефактам и другому общему изменяемому состоянию.
Пакеты с пересекающимися или конфликтующими поверхностями записи не выполняются
параллельно.

### `IG-MA-03` — Готовность зависимостей

Параллельно запускаются только рабочие пакеты, которые не зависят от ещё не
реализованного результата другого пакета. Появление готовой зависимости
открывает возможность заново оценить параллельную работу.

### `IG-MA-04` — Адаптивная параллельность

Количество субагентов определяется реальной шириной независимой работы,
доступными ресурсами и стоимостью последующей интеграции и проверки.
`issue-grinder` не создаёт фиктивные пакеты только ради использования свободных
слотов или достижения заданного уровня параллельности.

### `IG-MA-05` — Один владелец интеграции

Основной агент остаётся единственным координатором и владельцем Goal, изменений
в Task Manager, общего интегрированного результата и его окончательной
проверки. Только основной агент объединяет результаты субагентов.

### `IG-MA-06` — Изоляция авторов изменений

Каждый субагент, который изменяет код параллельно с другими авторами, до первой
записи получает отдельный Git worktree и отдельную `feature branch`,
привязанные к его конкретному рабочему пакету или issue.

### `IG-MA-07` — Исключительное владение worktree

Один Git worktree с правом записи одновременно принадлежит только одному
автору. Субагент не изменяет интеграционную ветку, чужой worktree или ветку
другого рабочего пакета.

### `IG-MA-08` — Read-only роли без отдельного worktree

Субагентам, которые только исследуют состояние или проверяют результат и не
изменяют файлы, отдельный worktree не требуется. Такие роли можно использовать
параллельно даже тогда, когда безопасна только одна полоса записи.

### `IG-MA-09` — Контракт рабочего пакета

Каждый субагент получает ограниченный scope, принадлежащие ему поверхности,
необходимые исходные данные, существенные ограничения, ожидаемый результат и
способ его проверки.

### `IG-MA-10` — Проверка интегрированного результата

Отчёт субагента и успешные проверки в его изолированном worktree не доказывают
общий результат. После объединения изменений основной агент проверяет точную
интегрированную версию.

### `IG-MA-11` — Повторная диспетчеризация

После завершения или блокировки рабочего пакета, изменения scope либо появления
готовой зависимости основной агент заново оценивает доступную независимую
работу, состав субагентов и степень полезной параллельности.

### `IG-MA-12` — Продолжение существующей работы

Незавершённые ветки и worktree, однозначно связанные с рабочим пакетом или
issue, сохраняются как контрольные точки. После подтверждения, что прежний
автор остановлен и параллельного владельца нет, новый эксклюзивный владелец
продолжает существующую работу, а не начинает её заново. Одновременно писать в
один worktree двум авторам запрещено.

### `IG-MA-13` — Приоритет пользовательского профиля

Если пользователь явно выбрал модель или уровень рассуждений для всех либо
отдельных субагентов, этот выбор имеет приоритет и не подменяется молча.

### `IG-MA-14` — Luna Max для простой работы

Без отдельного пользовательского выбора `gpt-5.6-luna` с `effort: max`
используется только для рабочего пакета, который одновременно:

- является автономным, ограниченным и самодостаточным;
- имеет ясные входные данные, ожидаемый результат и критерии проверки;
- владеет непересекающимися поверхностями;
- даёт объективно проверяемый результат;
- не требует существенного продуктового, творческого, архитектурного или
  межзадачного решения;
- не несёт существенного риска и не зависит от непредсказуемого состояния
  среды или инструментов.

Маленький diff, небольшое количество файлов или внешне механическая работа сами
по себе не делают пакет простым.

### `IG-MA-15` — Текущий профиль для остальной работы

Все рабочие пакеты, которые не соответствуют строгому определению простой
работы из `IG-MA-14`, наследуют модель и уровень рассуждений основного агента.

### `IG-MA-16` — Возврат работы с Luna основному агенту

Если Luna обнаружила неоднозначность, конфликт контекста или требований,
неожиданное состояние среды или инструментов, необходимость расширить scope
либо невозможность доказать результат, она прекращает изменяющие действия. Она
фиксирует уже выполненную работу, затронутые поверхности, доступные
доказательства и оставшуюся неопределённость и возвращает тот же пакет
основному агенту.

Основной агент продолжает пакет на своём текущем профиле. Повторно отправлять ту
же неразрешённую проблему в Luna запрещено.

### `IG-MA-17` — Недоступность Luna не блокирует работу

Если автоматический профиль Luna Max недоступен, рабочий пакет выполняется на
текущем профиле основного агента и прогон не блокируется только из-за
недоступности Luna.

### `IG-MA-18` — Strategic Explainer вне model routing рабочих пакетов

Профиль Strategic Explainer не выбирается правилами Luna для рабочих
субагентов. Strategic Explainer самостоятельно управляет своим исполнением
через собственный интерфейс.
