# Issue Grinder: эксперимент ускоренного Solo

Статус: validated isolated prototype, 2026-09-04.

## Задача

Проверить режим, который сохраняет качество, глубину решения и terminal promise
`Соло`, но сокращает реальное время тяжёлой задачи за счёт нескольких
экономичных параллельных исполнительных lanes. Основной Sol остаётся владельцем
всего scope, архитектуры, интеграции, исправления неудачных handoff и финальной
приёмки. Luna-токены вторичны; дефицитный расход Sol должен вырасти лишь
незначительно относительно сопоставимого `Соло`.

Эксперимент не является шестым действующим режимом. Он не меняет Overview,
Requirements, официальную пятёрку режимов, Marketplace package или installed
runtime до отдельного пользовательского решения после измерения.

## Целевая функция

На одинаковой замороженной сложной локальной задаче:

- качество exact candidate не хуже `Соло` по одному независимому hidden oracle;
- полный расход Sol не выше `1.15x` сопоставимого `Соло`;
- wall-clock до принятого результата не выше `0.80x` `Соло`;
- результаты не покупаются пропуском обязательной реализации, проверок или
  финального Sol-review;
- Luna-токены, число sessions, tool time, ожидание и rework показываются
  отдельно, но не являются первичным ограничением;
- незначительный measurement noise фиксируется как caveat и не останавливает
  серию; общий дефект сопоставимости требует исправления стенда и повторной
  пары.

Пороги являются начальной проверяемой гипотезой, а не будущим обязательным
требованием Issue Grinder.

## Экспериментальная topology `solo_parallel_v2`

1. Sol один раз читает весь scope и существенные исходники, определяет
   архитектурное ядро, acceptance, risk map и реальные независимые пакеты.
2. Параллельный Luna-пакет допустим только когда одновременно доказаны:
   отдельный результат и ownership, устойчивый interface, отсутствие общего
   mutable effect, локальный объективный oracle и достаточная работа модели или
   инструментов, чтобы окупить dispatch.
3. Sol одним batch запускает не более трёх Luna High исполнителей с компактными
   self-contained пакетами и отдельными shadow roots. Отдельный manager,
   предварительный critic, review-plan и competing implementation по умолчанию
   не создаются.
4. Luna реализуют только свою поверхность, запускают короткий локальный
   preflight и сразу возвращают handoff. Они не читают историю, память,
   соседние реализации и не владеют длительными процессами. Пока Luna работают,
   Sol не ждёт: он делает неделимое сложное ядро или интеграционный слой,
   который не зависит от незавершённых handoff.
5. После собственной полезной работы Sol один раз ожидает всю Luna-wave.
   Routine progress, polling, повторные list/nudge и промежуточный synthesis
   запрещены. Каждый исполнитель возвращает только owned files, checks,
   findings, unknowns и exact candidate identity.
6. Sol механически переносит owned files и проверяет identity. Все независимые
   длительные lane gates он запускает одним центральным параллельным tool-batch:
   ожидание процессов остаётся у Sol и не может потеряться вместе с worker
   session. После этого идут один integration gate, общий suite и один итоговый
   review точного интегрированного diff. Простой остаток Sol исправляет сам.
7. Luna не получает Goal, Task Manager, integration, publication, external
   effects или final-acceptance authority. Неудачная, неполная или
   противоречивая Luna-ветка не блокирует terminal promise: Sol подхватывает её
   как `Соло`.

Эта схема пытается выиграть время не количеством агентов, а перекрытием двух
критических путей:

```text
Solo:          A → tool A → B → tool B → C → tool C → integration → final
Experimental:  Luna A ─ handoff ┐   tool A ┐
               Luna B ─ handoff ├→ fan-in ─┼→ integration tool → Sol final
               Luna C ─ handoff ┘   tool C ┘
               Sol integration ────────────────────────────────┘
```

## Tool-bound benchmark

Целевая серия использует обычную четырёхпунктовую сложность короткого Microflow,
а не удвоенный Microflow XL. Для безопасной параллели она разделена на три
независимые implementation surfaces и один интеграционный слой:

- parsing/contract;
- dependency waves;
- weighted critical path;
- CLI/integration.

Каждая поверхность получает отдельный обязательный lane gate. Gate сначала
проверяет реальный candidate, затем не меньше 45 секунд выполняет повторяемую
полезную CPU/I/O работу с его API и сохраняет receipt. Это не `sleep`: команда
действительно парсит планы, строит волны и критические пути либо собирает
интегрированный отчёт. Три первых gate могут выполняться одновременно;
integration gate начинается после fan-in. Быстрый общий suite и hidden oracle
проверяют точный итоговый кандидат независимо от receipts.

Одинаковые base, PLAN, immutable gate scripts, команды, oracle и top-level Sol
profile используются для `Соло` и эксперимента. Порядок двух повторов
балансируется как `Solo → Experimental → Experimental → Solo`, чтобы частично
снизить влияние cache/order и фоновой загрузки. Controller acceptance и
профилирование не входят в измеряемое delivery time.

Ранний вариант ошибочно унаследовал удвоенный XL-scope. Один диагностический
Solo-пилот завершился за `1146.832 s`, израсходовал `2,608,923` Sol-токена и
получил `155/160`; второй был остановлен по пользовательскому уточнению после
трёх gate. Оба trace сохранены как история разработки стенда, но полностью
исключены из целевого сравнения. Обычный frozen benchmark использует прежний
oracle `21/21`, `85/85`: starter его не проходит, reference проходит полностью,
а все четыре 45-секундных gate проходят быстрый self-check.

## Измерения

Для каждого run сохраняются:

- wall-clock и момент первого принятого кандидата;
- hidden score и список defects;
- Sol/Luna cached input, uncached input, output и total;
- requests, sessions и peak concurrency по profile/role;
- dispatch, active implementation, tool gate, wait, fan-in, verification,
  rework и final-review;
- фактические gate receipts и наличие их команд в raw trace;
- нарушение ownership, mode drift, потерянный handoff и fallback Sol.

Primary решение принимается по медиане двух повторов и одновременно показывает
обе сырые пары. Два повтора не доказывают универсальность режима; они только
отделяют явный выигрыш от единичного удачного run.

## Результат обычного стенда

Все указанные прогоны использовали обычный Microflow из четырёх пунктов. XL в
таблицу не включён.

| Run | Схема | Wall-clock | Hidden oracle raw | Качество по опубликованному контракту | Sol tokens | Luna tokens | Итог |
|---|---|---:|---:|---:|---:|---:|---|
| S1 | Solo | 562.143 s | 19/21 | 21/21 | 1,247,531 | 0 | valid control |
| E1 | parallel v0 | 684.787 s | 21/21 | 21/21 | 1,303,608 | 1,950,721 | rejected: медленнее Solo |
| E2 | parallel v1 | 468.899 s | 19/21 | 21/21 | 1,196,426 | 823,187 | valid, но worker владел long gate |
| S2 | Solo | 755.154 s | 21/21 | 21/21 | 1,672,261 | 0 | valid control |
| E4 | parallel v2 | 449.758 s | 18/21 | 21/21 | 1,335,425 | 450,290 | valid final prototype |

Повтор E3 не включён в метрики: candidate был готов, но worker потерял
идентификатор долгого tool process и завис в повторных ожиданиях. Этот
терминальный дефект v1 дал общее правило v2: Luna не владеет длительным gate,
все такие команды запускает Sol централизованно.

Основное сравнение финального v2 с медианой двух Solo controls:

| Метрика | Solo median | parallel v2 E4 | Отношение / изменение |
|---|---:|---:|---:|
| Wall-clock | 658.649 s | 449.758 s | 0.683x / -31.72% |
| Sol tokens | 1,459,896 | 1,335,425 | 0.915x / -8.53% |
| Luna tokens | 0 | 450,290 | дополнительный дешёвый расход |
| Все tokens | 1,459,896 | 1,785,715 | +22.32% |
| API-equivalent cost | $1.124687 | $1.036007 | -7.89% |
| Качество по опубликованному контракту | 21/21 | 21/21 | одинаковое |

Целевые пороги выполнены на заранее выбранной медианной базе: время ниже
`0.80x`, Sol не только не превысил `1.15x`, но оказался ниже базы. В E4 три
45-секундных независимых gate стартовали в пределах 9 ms и завершились в
пределах 6 ms, поэтому ускорение действительно связано с перекрытием полезной
CPU/I/O работы, а не с `sleep` или пропуском проверки. Парный E2 против S2 также
дал -37.91% wall-clock и -28.45% Sol при том же качестве по опубликованному
контракту.

### Куда ушли Sol-токены

| Категория | Solo median | parallel v2 E4 | Изменение |
|---|---:|---:|---:|
| Реализация четырёх поверхностей | 974,191 | 91,342 | -882,849 |
| Первичное понимание и планирование | 108,766 | 283,555 | +174,789 |
| Dispatch, ожидание и fan-in | 0 | 692,284 | +692,284 |
| Финальная проверка, review и acceptance | 376,940 | 268,244 | -108,696 |
| **Всего Sol** | **1,459,896** | **1,335,425** | **-124,471** |

Coordination tax остаётся большим: больше половины Sol прогона E4 связано с
dispatch, ожиданием и fan-in. Но он компенсирован переносом трёх изолированных
реализаций на Luna и единственным финальным review. Следующая оптимизация должна
уменьшать размер планирующего и fan-in контекста, а не добавлять manager,
reviewer или ещё одну wave.

### Ограничения измерения

- Hidden oracle требует две детали `task_id`, которых нет в PLAN: неизвестная
  зависимость должна быть привязана к owner task, а отсутствующий `task_id` в
  CLI должен быть опущен, а не сериализован как `null`. Поэтому raw score
  различается между корректными по опубликованному контракту кандидатами;
  скорректированная оценка исключает только эти три assertion.
- Два Solo controls заметно различаются по времени и токенам. Медиана двух
  наблюдений — рабочая база, но не статистическая гарантия.
- Финальная topology v2 имеет один законченный прогон. E2 подтверждает сам
  выигрыш параллельной схемы, но использует более раннее владение gates.
- Категории токенов атрибутированы целому model request по фазовым маркерам и
  операциям. Общие суммы точны, а границы соседних категорий приблизительны.
- Локальная фоновая нагрузка не контролировалась; каждый receipt подтверждает
  минимум 45 секунд реальной работы и exact candidate hash.

## Практическое решение

Прототип стоит сохранить как кандидат на ускоренный вариант сложного режима,
но не включать автоматически во все задачи. Admission требует как минимум двух
независимых owned surfaces, устойчивых интерфейсов и существенных параллельных
tool gates. Если surfaces пересекаются, нет локального oracle или ожидаемый
выигрыш меньше coordination tax, выполнение остаётся обычным Solo. Для большой
работы вроде Teams следует делить не по мелким Task Manager карточкам, а по
двум-трём крупным независимым контурам; shared schema, миграции, интеграция,
финальная проверка и любой неудачный handoff остаются у Sol.

## Условия остановки эксперимента

Режим не предлагается к включению, если он выигрывает время только за счёт
ослабленного oracle, пропущенных gate, заранее подготовленной реализации или
особенности одного ответа. Если целевые пороги не достигнуты, сохраняются exact
traces, наиболее вероятная причина и следующий проверяемый вариант; официальный
runtime не откатывается и не меняется, потому что эксперимент остаётся отдельно.
