# Парная проверка Balance: ускорение не достигнуто

Дата: 2026-09-04. Статус: четыре измерения завершены; улучшение целевой функции не подтверждено.

## Результат

На обычном четырёхпакетном Microflow новая итерация Balance в среднем медленнее
Solo на 53,4%, расходует на 27,3% больше Sol и на 32,9% дороже по
зафиксированным API-ставкам. Все четыре результата получили 85/85 без поправок.
Из двух попыток на режим нельзя получить устойчивую оценку для реальных
проектов, но в этой серии ни один Balance не обогнал ни один Solo.

## Что изменено и проверено

- Уточнены опубликованные формат CLI error и значение task_id; добавлен публичный
  тест двух примеров. Эталон проходит публичные и 21 скрытую проверку, starter
  ожидаемо их не проходит.
- Runtime скопирован в отдельный frozen-skill; SHA-256 до и после каждого запуска
  совпадает: `7bf18f9e6803c0ba9d0cdfcd7e4e14841146bbfb26026f6315864bd46e67d583`.
- Architecture и Balance runtime требуют пакетной подготовки независимых
  проверок, компактного handoff и однократной сверки bytes вместо повторных
  полных чтений. Requirements и Overview не менялись.
- Порядок: S5 → B5 → B6 → S6; один и тот же Sol xhigh, Luna workers high,
  четыре 45-секундные реальные вычислительные проверки, timeout 3600 секунд.
- Независимый маленький probe Luna manager вернул capability gap: у child нет
  collaboration messaging/wait/followup. Полный Manager не запускался.
  Это проверка отсутствия прямого интерфейса текущего child; универсальная
  невозможность программного relay этим не доказана.

## На что ушёл Sol

Средние по двум попыткам; округление до токена. Категория определяется
последним явным фазовым маркером. Поэтому реализация может включать локальные
gates, review — исправления и их проверки, coordination — подготовку изоляции,
ожидание и fan-in. Это атрибуция по стадии, а не точное выделение reasoning.
Суммы без округления сходятся с рекурсивным деревом во всех четырёх запусках.

Balance экономит около 584 тыс. Sol на реализации, но добавляет около 994 тыс.
на остальных стадиях; чистая прибавка — 410 тыс. Sol.
Результат не объясняется одним только cache: uncached Sol input вырос в среднем
с 66 586 до 74 856,5, output — с 14 685,5 до 19 737,5.

## Причины и существенные оговорки

Первая рабочая Luna запущена через 177,915 секунды в B5 и 164,146 в B6;
в предыдущем B4 — примерно 193 секунды. Выигрыш подготовки всего 15–29 секунд.
Рабочая волна и последующая приёмка занимают минуты.

B5 на финальном review исправил ошибку waves при повторённой зависимости
прямого Task, затем повторил waves/integration gates. B6 исправил собственный
Sol CLI после общей проверки: critical_path сериализовался списком вместо
объекта. Эти затраты необходимы для проверенного результата и не вычитаются
из wall-clock; приписывать их все Luna было бы неверно.

Прежние 77/85 у Manager/Economic нельзя уверенно называть реальными дефектами:
старый PLAN не задавал точный формат error JSON, хотя hidden oracle требовал его.
Raw исторические результаты не переписаны. Новая пара использует уточнённое
задание, поэтому это новая серия, а не строгий A/B только текстовой правки.
Старый и новый Balance на одинаковом исправленном контракте не сравнивались;
причинно приписывать всю разницу данной правке нельзя.

Во всех новых runs: exit 0, timeout отсутствует, 4/4 receipts валидны, frozen
source и PLAN не изменены, запрещённых внешних tools нет. Solo не создавал
execution children; каждый Balance создал ровно трёх Luna High workers.

## Публикация и дальнейшее решение

Runtime-изменение: ShipTask `35655f1`; Marketplace `01af921`;
установленный Issue Grinder `0.1.0+codex.20260904223200`.
Свежий App Server initialize → initialized → skills/list(forceReload=true)
подтвердил новый enabled snapshot. Источники четырёх актуальных skills
побайтно совпали с Marketplace и installed cache. Legacy ship-tasks не установлен;
Task Manager остался отдельным enabled adapter.

161 тест ShipTask прошёл. В чистой копии прошли validate_repo, пять skill
validators и проверка 357 локальных ссылок. Общий Marketplace suite:
27/28; отдельно не прошла воспроизводимость mind-diary-local-darwin-arm64.
Бинарник и исходники Example Notes данной правкой не менялись; Issue Grinder
plugin validation прошёл.

Новая итерация оставлена установленной, но не объявляется улучшением.
Автоматический rollback не выполнялся. Подготовлен обратный патч только
Architecture/Evaluation/Balance runtime, который возвращает состояние до
итерации. После его применения потребуются проверки, новая публикация и
обновление installed snapshot; не редактировать installed cache напрямую.

Следующий полезный эксперимент — один воспроизводимый механизм подготовки и
сборки изолированных пакетов с машиночитаемыми receipts, который сокращает
отдельные ходы Sol. Его сначала стоит проверять дешёвым техническим сценарием.
Очередное наращивание текста инструкций без такого механизма не обосновано.
Полный Manager имеет смысл измерять после working transport без routine Sol relay.
Проверка на другом workload не запускалась: условие повторяемого выигрыша
основной серии не выполнено.
