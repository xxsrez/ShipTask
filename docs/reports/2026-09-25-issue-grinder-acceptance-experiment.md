# Issue Grinder: эксперимент с сохранением приёмки длинного Release

Дата: 2026-09-25. Проверка синтетическая, на `gpt-6-sol` с `xhigh` — это профиль
исходного проблемного run. В Task Manager, UAT и Production эксперимент не
обращался. Текущие user-owned Overview и Requirements оставлены без правок.

## Результат

Единственный устойчивый измеренный выигрыш дала короткая карта в существующем
checkpoint: **ID каждого открытого критерия → полученное доказательство с
кандидатом и условиями → оставшийся пробел** по всему активному scope. В
последнем, не использованном при настройке наборе текущий установленный skill
дал **9/10** ответов с полным списком открытых критериев, кандидат — **10/10**.
В ранее отложенном наборе результат был **8/10 → 10/10**, но он уже
использовался для уточнения формулировки. Baseline в промахах понимал, что
Release нельзя закрывать; тест не доказывает снижение числа ложных закрытий
в живом run.

Прямые одношаговые решения: **11/11 у baseline и 11/11 у кандидата**. Пять
других уточнений дали равенство на своих сценариях и удалены из итогового
изменения. Рост входных токенов на последнем двухшаговом наборе: 456 638 →
459 380 за 20 вызовов модели, около **0,6%** в этой искусственной процедуре.
Выходных токенов было 8 161 → 7 224; разницу нельзя приписать правилу по
такому малому набору.

## Как измеряли

Baseline — установленный `issue-grinder@0.1.0+codex.20260925115611`, reference
`run-and-goal.md` с SHA-256
`85e368b6e7a0a0412a3b53fdc35acb82cd0e60c6a342b6b334469348f54765f3`.
Кандидат отличается только `architecture.md` и соответствующим абзацем в
`run-and-goal.md`; его reference SHA-256 до публикации:
`93f08ea2f11143d2c6078617e5dd24255d5b0f3dd9b3069a9c137a59c814c89f`.
Остальной runtime совпадал с baseline.

Использованы [одношаговый harness](../../scripts/issue_grinder_acceptance_experiment.py)
и [двухшаговый harness](../../scripts/issue_grinder_continuity_experiment.py).
Каждый вызов — отдельный `codex exec --ephemeral --ignore-user-config
--sandbox read-only`. В двухшаговом тесте первый вызов получает ограничение
checkpoint в 65 слов, второй видит только checkpoint и новую заметку.
Оцениваются выбор действия, текущий статус, отсутствие ложного запроса человеку
и точные ID открытых критериев. Тексты решений прочитаны вручную; сходные по
смыслу `inspect_route` и `preserve_review` не объявлялись ошибкой действия.
При подсчёте ID принимался и формат `T-1301: AC-READ`, но описание критерия
без его существующего ID не засчитывалось.

Перед вариантами зафиксированы сценарии прямого решения и первичного
продолжения. В пилоте обнаружены и исправлены ошибки оракула: уже выполненный
terminal write был принят за будущий, а возврат резервации за 62 секунды
ошибочно назван подтверждением лимита 60 секунд. Эти результаты исключены из
сравнения. Дополнительные многозадачные случаи и закрытый holdout созданы до
их прогонов. SHA-256 финального прямого набора:
`3236a1ddcc2912682656e118345624e69af5f843e93edaed0cb149027a5804b7`;
закрытого holdout:
`43c4cbcdd10ff427cdebd05fd30559ea83bc26db346c2ccfa2a342a25280c955`.

## Промежуточные варианты

| Уточнение runtime | Baseline → вариант | Вывод |
|---|---:|---|
| Рано выяснять путь доказательства до существенной переделки | 2/2 → 2/2 прямых; сохранение UAT-маршрута после checkpoint также было верным у обоих | Прироста нет; убрано |
| Карта доказательств без точных ID | 0/2 → 0/2 по полному списку ID в многозадачном случае | Не помогло; уточнено |
| Карта с ID каждого открытого критерия | 0/2 → 2/3 по полному списку ID в tuning; на первом отложенном случае 2/3 → 3/3 | Сохранено для финальной проверки |
| Мягкая оговорка «если ID нет, используй ссылку» | 8/10 → 8/10 на повторе прежнего holdout | Потерян выигрыш по существующим ID; убрано |
| Различать ремонт тестового клиента, продукт и очистку | 3/3 → 3/3 | Прироста нет; убрано |
| Перед дорогим повтором уточнять гипотезу и изменённые входы | 6/6 → 6/6 с контролем, где повтор обязателен | Прироста нет; убрано |
| Проверять новый hosted-маршрут на малом сценарии | 3/3 → 3/3 | Прироста нет; убрано |
| Объединять исправления перед CI и ждать событие review | 3/3 → 3/3 | Прироста нет; убрано |

В первом отложенном многозадачном случае автоматический счётчик давал 3/6 для
baseline и 4/6 для кандидата, но часть промахов была лишь выбором другого
подходящего имени действия. По содержанию решений оба оставляли Release
открытым. Метрика, ради которой оставлено изменение, — **полный список точных
ID**, а не формальная частота одного слова в JSON.

## Отложенные наборы

В `final_holdout_search_delete` после закрытия последней обсуждавшейся
карточки оставались два обязательства других карточек: поиск с фильтром доступа
вторым пользователем и штатное удаление дочерних файлов. Baseline сохранил оба
смысла, но назвал оба ID лишь в 3 из 5 прогонов. В одном ответе список ID был
пустым, в другом вместо `AC-SEARCH` использовано описание критерия с пометкой,
что ID потерян. Финальный кандидат сохранил оба ID в **5/5** на повторе.

В новом `sealed_holdout_read_revoke` открыты чтение вторым UAT аккаунтом и
проверка отказа после revoke. Baseline сохранил оба ID в **4/5** прогонов,
финальный кандидат — в **5/5**. Второй новый контроль имел обязательный
критерий вообще без стабильного ID: обе версии сохранили его текстовую ссылку
и не придумали ID в **5/5** прогонов. Для финального кандидата это **10/10**
по закрытому набору против **9/10** baseline.

Контроль `final_holdout_true_owner` требовал реальной подписи внешнего владельца
после проверки всех доступных путей. Обе версии правильно просили точное
действие и оставляли задачу в `In Review`: **5/5 и 5/5**. Прямой набор,
включавший обязательный повтор после изменения ACL, допустимое закрытие и
независимое review, также прошёл **11/11 и 11/11**.

Эксперимент измеряет решения на короткой синтетической передаче состояния.
Он не воспроизводит 14 часов работы, реальное сжатие платформой, изменение
Task Manager, фактическое получение UAT receipts или расходы полного Release.
Один дополнительный полный список в последнем закрытом наборе и два в
предыдущем — основание для узкого изменения checkpoint, но не гарантия лучшей
живой приёмки. Следующая проверка
после установки — свежая сессия с установленным skill и затем наблюдение
нового настоящего run по тем же исходам.
