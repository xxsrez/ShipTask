# Luna-координатор с Sol для сложной работы: одинарный Microflow

Дата: 2026-09-06. Статус: эксперимент LC1 завершён; действующие режимы не изменены.

## Результат

Luna Max самостоятельно реализовала одинарный Microflow и выполнила проверки.
Один независимый Sol Extra High проверил готовый кандидат. Внешняя скрытая
приёмка — **21/21, 85/85**, без изменения oracle и без передачи его результатов
исполнителям. Все четыре исходные вычислительные проверки по 45 секунд действительны.

Относительно последнего замера Sol Соло S6: **−82,7% токенов Sol, −60,2%
расчётной стоимости, −8,8% всех токенов**, но **+21,7% времени**.
Стоимость одного принятого результата в этой паре ниже в **2,52 раза**.
Это положительный одиночный результат проверки экономичности, не доказательство
устойчивого превосходства или готовности нового режима к установке.

## Решение, которое проверяли

Постоянная сессия работает на Luna Max. Она исследует код, реализует обычную
работу, исправляет локальные ошибки, ведёт план и ожидает процессы. Sol xhigh
получает ограниченный вопрос либо целый сложный участок при противоречии,
неясном общем интерфейсе или двух разных безрезультатных попытках. Внутри
переданного участка Sol отвечает за результат, без пошаговой переписки.

Перед приёмкой обязателен один независимый Sol-reviewer: исходные требования,
кандидат, существенные риски и собственные целевые проверки. Если Sol ранее
реализовывал код, reviewer должен быть другим неавтором. Сложная реализация и
эскалация здесь разрешены протоколом, но фактически не понадобились — проверена
ветка «Luna реализует → Sol проверяет», а не способность Luna правильно
распознать сложную задачу и передать её Sol.

Наследование полной истории выключено; один собранный ответ от специалиста;
ожидание по событию; повторное использование reviewer при существенной
доработке. Только один writer одновременно. Новых требований к результату,
внешних сервисов и публикации нет.

## Что наблюдалось

- Подтверждены две сессии: корень `gpt-5.6-luna/max` и независимый
  `gpt-5.6-sol/xhigh`; лишних execution-потомков нет.
- Luna сделала реализацию сама, выполнила публичные 5 тестов, четыре gate и
  дополнительные проверки CLI. У неё 24 инструментальных вызова верхнего уровня,
  включая один spawn и один событийный wait.
- Sol сделал 6 инструментальных вызовов: изучение исходных требований и кода,
  публичные тесты, проверка diff и независимые целевые проверки. В журнале есть
  успешная проверка контрактов ошибок, сохранности output и **500 случайных DAG**.
  Итоговая приёмка root фиксирует `accepted`; повторной передачи на исправление нет.
- Gate выполнялись последовательно и заняли суммарно около 180 секунд работы.
  Общий результат медленнее S6 примерно на 1 минуту 57 секунд. Без отдельного
  сравнения нельзя весь проигрыш по времени приписать одному механизму.
- Sol использовал лишь 19,0% всех токенов, но сформировал 88,3% стоимости LC1:
  $0,380308 против $0,050282 у Luna. Следующий потенциальный резерв — стоимость
  достаточного ревью и его входного контекста; отключение ревью здесь не проверялось.

## Метод и целостность

Один новый запуск LC1, без подбора лучшего из серии и без вмешательства в
измеряемую сессию. Обычные четыре задачи MF-1…MF-4, не удвоенная нагрузка.
Использован старый runner и неизменные base/oracle/gate из уточнённой серии v7.
Пустая заготовка провалила oracle, эталон прошёл его перед стартом.
Тайм-аут — 3600 секунд; завершение с exit 0 за 659,167 секунды.

LC1: UTC `[2026-09-06T19:38:11.973Z, 2026-09-06T19:49:11.148Z)`;
на Мадейре 20:38:11,973–20:49:11,148. Измерение исключает подготовку этого
эксперимента, исследующего агента, написание отчёта и внешний детерминированный
oracle. Это стоимость повторяемого исполнения, не полная стоимость исследования.

Код кандидата сохранён как локальный diff и новый `_graph.py` в isolated
workspace, не выдан за commit. Зафиксированы SHA256 всех его модулей.
Проверены неизменность tools/README/example, семантики PLAN и всех действующих
source-файлов Issue Grinder. Ничего из реализации кандидата после первого
запуска gate не менялось по доступным файловым временам. Старые receipts
хешируют фиксированный список, поэтому отдельный манифест всех модулей добавлен
как дополнительное свидетельство, а не как подмена исторических receipts.

Новый протокол компактнее production skill и **заменяет его загрузку** для
локального эксперимента. Поэтому это совместная проверка маршрутизации и
компактной организации работы. Нельзя утверждать, что замена модели корня
сама по себе дала весь эффект. Полный Task Manager lifecycle, восстановление,
конкурентные writers, UAT и сложные эскалации не проверялись.

## Решение по итогам

Гипотеза экономии получила положительное свидетельство на одном небольшом
контракте: Luna закрыла реализацию, Sol обеспечил независимую проверку, качество
по общей приёмке сохранилось, расход дорогой модели существенно снизился.
Общее число токенов уменьшилось умеренно; основной эффект — перенос работы на
дешёвую модель. Ускорение относительно Соло не достигнуто.

Схему имеет смысл проверять дальше на задачах с настоящей необходимостью
эскалации. Данный результат не разрешает ослаблять требования к качеству и
не превращает протокол в установленный режим. Overview, Requirements,
Architecture, runtime и Marketplace не изменены.

План эксперимента завершён: исторические данные восстановлены и сверены,
протокол заморожен и исполнен, качество/топология/токены проверены, сравнение
с ограничениями сохранено. Доказательства приведены отдельно выше; завершение
плана само по себе не использовалось как свидетельство качества.

Проверка документации: `validate_docs.rb . --strict-navigation` — успешно,
82 документа и 360 локальных ссылок; `git diff --check` — успешно.
Полный набор runtime-тестов не запускался: runtime не изменён.
