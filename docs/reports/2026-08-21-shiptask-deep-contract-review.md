# Глубокая ревизия ShipTask

Дата: 2026-08-21.

## Цель

Проверить весь действующий контракт ShipTask, убрать внутренние противоречия и
оставить один однозначный ответ на вопросы о приёмке, статусах, комментариях,
повторных попытках, Goal и роли Strategic Explainer.

## Как проводилась ревизия

Ревизия состояла из трёх отдельных проходов.

1. **Lifecycle и приёмка.** Сопоставлены specification, runtime `SKILL.md`,
   обзор, development guide, review matrix, runtime references и ADR.
2. **Полномочия и объяснение результата.** Проверены границы Task Manager
   adapter, Goal, release authority, comment channel, bounded repair и
   Strategic Explainer.
3. **Структура и наследие.** Проверены дублирование, устаревшие формулировки,
   навигация документации, distribution contract, длина runtime skill и смысл
   repository validator.

## Устранённые противоречия

### Значение `In Review`

Раньше часть документов называла любую Task в `In Review` уже проверенным
кандидатом, а другая часть требовала сначала установить её фактический исход.
Теперь `In Review` нейтрален: result предъявлен, но один status не доказывает ни
успех, ни defect, ни пройденную проверку.

### Четыре исхода приёмки

Каждая `In Review` Task после одного ограниченного диагностического прохода
получает ровно один исход:

- противоречие или существенный пробел в постановке;
- доказанный успех;
- доказанный defect;
- невозможность сейчас доказать ни успех, ни defect.

Длинная история изменений acceptance сама по себе не считается противоречием.

### Падение общей проверки

Раньше один документ отправлял на доработку весь связанный batch, если общая
проверка упала и виновная Task неизвестна. Теперь на доработку возвращается
только Task с прямым доказательством defect. Неразличимые Tasks остаются
`In Review`, пока отдельная диагностика не установит причину.

### Статус и комментарий

Раньше сбой записи любого комментария мог удерживать Task в ложном статусе.
Теперь terminal report по-прежнему обязателен перед новым `Done` или
`Canceled`, но недоступный `REWORK REQUIRED` не оставляет доказанно сломанный
result в `In Review`. Недоступный `BLOCKED` не меняет уже установленный исход;
текст сохраняется в итоговом отчёте как незавершённая публикация.

### Повторные попытки и Goal

Удалено правило о трёх одинаковых попытках или трёх ходах Goal. Одна и та же
проверка не повторяется без названного изменения result, среды, доступа,
полномочий, механизма проверки или Task contract. Локальная блокировка Task не
переводит весь Goal в `blocked` и не создаёт искусственный цикл.

### Strategic Explainer

Strategic Explainer обязательно формулирует понятное объяснение для
`COMPLETED`, `REWORK REQUIRED`, `BLOCKED` и `CANCELED`, но не выбирает статус,
полномочия или действие. Для невозможной приёмки он сравнивает 2–4 способа
получить недостающее доказательство. После одной исправленной попытки запуска
технический сбой Explainer обрабатывается локальным применением того же
контракта и не становится новым blocker Task.

### Форма отчёта

Удалено требование обязательной диаграммы для любой сложной Task. Диаграмма или
таблица нужна только тогда, когда действительно упрощает понимание нескольких
связанных состояний, участников или шагов.

## Структурный рефакторинг

- Runtime `ship-tasks/SKILL.md` сокращён примерно с 485 до 296 строк: подробные
  объяснения остались в specification и references, а исполнимый файл теперь
  содержит порядок действий и обязательные границы.
- Добавлен ADR-0016, который собирает действующие lifecycle/reporting правила и
  явно заменяет конфликтующие части ранних ADR.
- Старые ADR сохранены как история решений, но их заголовки прямо указывают,
  какие части больше не действуют.
- Task Manager adapter повторно сверен с установленным adapter-only plugin;
  старое утверждение о наличии в нём второго delivery workflow удалено.
- Исправлена нумерация требований Strategic Explainer.
- Repository validator заменён с проверки сотен точных фраз на проверку
  структуры, decision matrices, обязательных границ, запрещённых
  противоречий, supersession markers, ссылок и distribution contract.

## Действующий ответ на спорные ситуации

| Ситуация | Что делает ShipTask |
|---|---|
| Постановка противоречива | Исправляет только однозначную ошибку при имеющемся праве; иначе оставляет `In Review` и понятный `BLOCKED` с точным требуемым решением. |
| Defect доказан | Готовит `REWORK REQUIRED`, переводит Task в `In Progress` и начинает доработку. |
| Успех доказан | Публикует и перечитывает `COMPLETED`, затем переводит Task в `Done`. |
| Проверка ничего не доказывает | Оставляет `In Review`, объясняет границу знания и предлагает 2–4 способа провести приёмку. |
| Общая проверка упала без виновной Task | Не отправляет весь batch на доработку; сначала разделяет причины. |
| Канал комментариев недоступен | Не пишет отчёт в Task fields; переход в `Done`/`Canceled` ждёт отчёт, а незавершённый статус отражает уже доказанный исход. |

## Проверки исходников

После рефакторинга выполнены обязательные проверки repository:

```text
python3 scripts/validate_repo.py
python3 .../skill-creator/scripts/quick_validate.py ship-tasks
python3 .../skill-creator/scripts/quick_validate.py strategic-explainer
ruby .../project-docs/scripts/validate_docs.rb . --strict-navigation
git diff --check
```

Проверки подтверждают валидность обоих runtime skills, целостность локальных
ссылок, полноту навигации и отсутствие whitespace errors. Marketplace и
installed cache проверяются отдельно при каждой публикации и намеренно не
фиксируются в этом документе как вечное состояние.
